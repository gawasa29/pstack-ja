# 不具合を再現して修正する

ソーススレッドで、信頼できるトリアージの印を待ちます。対象アプリの実際の UI を通して、正確な症状を再現します。既存の修正があるときは、それを検証します。確認済みの再現が取れてからだけ、範囲を絞った修正を試みます。

オートメーションが渡す外部の Benny 設定を読み込みます。設定、必要なアクション、control アダプタ、記入済みの機能マップのどれかが欠けていれば、フェイルクローズ（fail closed）にします。

## 厳格な安全ルール

- 作業を始める前に、ソースチャンネルとルートスレッドの座標を固定します。
- ソースチャンネルにルートメッセージを決して投稿しません。
- ソーススレッドに投稿するたびに、その前にソースの親メッセージをプリフライトします。
- Slack に投稿できるのは調整役だけです。
- 委任された分析ワーカーは読み取り専用で、所見またはメディアのメモを返します。
- 修正フェーズのコードワーカーが編集できるのは、その環境から Slack の資格情報とすべての Slack への書き込みアクションが確実に排除されていることを証明できる場合だけです。そうでなければ調整役が編集します。
- 子のプロンプトはすべて、`SendSlackMessage`、`PostToSlack`、`chat.postMessage`、その他すべての Slack への書き込みを明示的に禁じる必要があります。
- 子に、Slack のトークン、投稿の指示、投稿用のソース座標、外部に報告する許可を決して渡しません。
- 子が動くのに Slack への書き込み権限を必要とするなら、その子は起動しません。
- ユーティリティ bot は証拠の出どころです。人が明示的に修正を委任した場合を除き、修正の所有者にはなりません。
- 判別力のある正確な症状が、実際の UI 操作を通して 2 回現れる必要があります。
- 状態の検査は、観察を裏付けることはできます。症状を注入したり、強制的に起こしたりしてはいけません。
- 確認済みの再現が無ければ、修正は書きません。
- 既存の pull request やコミットがあれば、実行は検証モードに切り替わります。その上に修正を書いてはいけません。
- pull request のリンクは `github.com` のものを使います。
- キャプチャ、録画、ログ、トークンをソース管理に入れません。
- 委任した分析には pstack の `principle-guard-the-context-window` を使います。
- 再現、修正、検証を通して、pstack の `principle-sequence-verifiable-units`、`principle-fix-root-causes`、`principle-prove-it-works` を適用します。

## 1. ソースの座標を固定する

作業リストを作る前、または委任する前に:

1. トリガーのチャンネルが、設定済みのソースチャンネルと一致することを必須にします。
2. `trigger.thread_ts` があれば、`SOURCE_THREAD_TS` にそれを設定します。無ければ `trigger.ts` を使います。
3. `SOURCE_THREAD_TS` が空でないことを必須にします。
4. `SOURCE_CHANNEL_ID` と `SOURCE_THREAD_TS` を不変の値として保持します。
5. ソーススレッドを読み、そのルートがまさにその座標を持つことを検証します。
6. ソースのパーマリンクを取得します。

これらの値を、返信のタイムスタンプ、運用のタイムスタンプ、ステータスメッセージのタイムスタンプで決して置き換えません。

ソースチャンネルに投稿するたびに、その前に:

1. 不変の座標でスレッドを読みます。
2. 親メッセージが存在し、削除されておらず、まだソースチャンネルに属していることを確認します。
3. `channel=SOURCE_CHANNEL_ID` と `thread_ts=SOURCE_THREAD_TS` だけで送信します。
4. もう一度スレッドを読み、新しいメッセージが返信になっていることを検証します。

チェックが 1 つでも失敗したら、何も投稿しません。ルートでもフォールバックのチャンネルでも、決してリトライしません。

## 2. トリアージの契約を待つ

設定済みの判定の予算の範囲で、ソーススレッドを監視します。待っている間は黙っています。

判定を受け入れるのは、次のすべてを満たすときだけです:

- その投稿者が `slack.triage_identity_user_id` と一致します。
- `SOURCE_THREAD_TS` の下の返信です。
- 設定済みの印をちょうど 1 つ含みます。

公開される印の形式:

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

進むのは `bug` か `performance` のときだけです。任意のトラッカー URL を取得します。`other`、判定が無い、信頼できない投稿者、競合する印、タイムアウトのときは、黙って止まります。

この印は、非公開の bot の身元と自由文での判定の照合に代わるものです。

## 3. 所有と修正の成果物のゲートを適用する

作業を始める直前に、スレッドを読み直します。

### 誰かが明示的に修正している

人が明確に修正を名乗ったとき、具体的な実装計画を示したとき、または別のエージェントに実装、パッチ、修正、pull request の作成を頼んだときは止まります。

次は修正の所有として扱いません:

- bot が証拠を要約する。
- ツールがログやチケットを調べる。
- 人が bot に診断、説明、検査、再現を頼む。
- bot が、実装に合意せずに原因の仮説を投稿する。

bot がいるかどうかではなく、頼まれたアクションで判断します。

### 修正の成果物がすでにある

オープンな pull request かマージ済みのコミットがこの報告を直す可能性があるなら、`references/verify-existing-fix.md` に切り替えます。

成果物は、スレッド、トラッカーの課題、リポジトリの履歴、pull request の検索から見つかることがあります。コミットや pull request を伴わない主張は、修正の成果物ではありません。

人が作業を所有しているのに成果物がまだ無いなら、止まります。その人と競争してはいけません。

## 4. 任意の運用スレッドを開く

`slack.operations_channel_id` が設定されていれば、調整役はそこにルートのステータスメッセージを 1 つ作ってもかまいません。再現ワークフローで許されるルート投稿は、これだけです。

その座標を `OPERATIONS_CHANNEL_ID` と `OPERATIONS_THREAD_TS` として保持します。ソースの座標と決して混同しません。

設定済みのプレーンな Unicode ステータス文字列を使います。ステータスの文は短く保ちます:

- 再現中（Reproducing）
- 再現できず（Could not reproduce）
- ブロック（Blocked）
- 再現済み（Reproduced）
- 既存の修正を検証中（Verifying existing fix）
- 範囲を絞った修正を試行中（Attempting bounded fix）
- ドラフト pull request を開いた（Draft pull request opened）
- 修正が入らなかった（Fix did not land）

設定済みの Cursor の Slack アクションを優先します。`BENNY_SLACK_BOT_TOKEN` を使うのは、この 1 つのステータスメッセージの編集など、狭く不足している機能のためにユーザーが設定したときだけです。トークンをワーカーに決して見せません。

運用チャンネルが設定されていなければ、詳細なステータスはオートメーションの実行出力に残します。ソースチャンネルのルートメッセージで代用してはいけません。

## 5. control アダプタを読み込んで確認する

`references/control-adapter.md` と、`control.feature_map_path` にある記入済みのマップを読み、`control.skill_name` が指すスキルを呼び出します。

報告されたユーザーパスに合う機能マップのセクションを探します。アプリを操作する前にそれを読みます。どのセクションもその機能を扱っていなければ、パスやセレクタをでっち上げるのではなく、実行をブロック済みにします。

次の 7 つの機能をすべて必須にします:

1. 設定済みの対象アプリとテスト環境を起動する。
2. マップ済みの機能へ移動し、文書化された状態を操作する。
3. クリック、入力、キー、スクロール、ドラッグ、リサイズ、移動で、実際の UI を操作する。
4. 状態を変更せずに検査する。
5. スクリーンショットを取得する。
6. 画面録画を開始・停止する。
7. プロセス、セッション、プロファイル、一時データを片付ける。

アダプタが無いか、必須の機能が 1 つでも欠けていれば、運用ステータスをブロック済みにして止まります。スクリーンショット、ユニットテスト、状態の変更、ソースの読み込みを、UI の再現であるかのように扱ってはいけません。

## 6. 報告を調べる

ソーススレッド全体と、あればトラッカーの課題を読みます。

集めるもの:

- 正確な操作パス
- 期待される振る舞い
- 観察された振る舞い
- 両者が分かれる、判別力のある状態
- 頻度
- バージョン、環境、プラットフォーム
- 添付とエラーのシグネチャ
- 候補となるコード領域

スクリーンショットと動画を調べます。必要に応じて、コードの履歴、テストのアイデア、影響範囲のマッピング、メディアのレビューに、読み取り専用の並列ワーカーを使います。各ワーカーには、狭い問いと Slack への書き込みの禁止を渡します。

その操作をリポジトリ全体でたどるには、pstack の `how` スキルを使います。回帰の履歴と防御的なコードには `why` を使います。競合する原因の仮説を立て、それらを切り分ける証拠を特定します。

## 7. 再現する

control アダプタを通して対象アプリを起動します。

操作する前に、正しいアプリ、ワークスペース、アカウント、データセット、機能の状態を確認します。安定したアプリマーカーを使います。ウィンドウの順序や、見慣れたタイトルだけに頼ってはいけません。

報告されたパスを、実際の UI 操作でたどります。

再現したと言う前に:

1. 正しい最終状態を名指しする。
2. 壊れた最終状態を名指しする。
3. 両者が分かれる地点まで到達する。
4. 壊れた状態を観察する。
5. 2 回目の試行を独立させるのに足る状態をリセットする。
6. 同じパスを繰り返し、同じ壊れた状態をもう一度観察する。
7. 可能なら、実際の状態の値を突き合わせる。

想定どおりのダイアログ、読み込み中の状態、セットアップの手順は、不具合ではありません。正しい振る舞いと壊れた振る舞いを分ける最終状態をキャプチャします。

設定済みの再現の予算を使います。その中で症状が再現しなければ、`Could not reproduce` を明快な結果として報告します。環境が必須の機能を提供できなければ、`Blocked` を報告し、何が欠けていたかを述べます。

## 8. 証拠をキャプチャしてレビューする

再現に成功した場合:

- 症状に至るパス全体を録画する。
- 壊れた最終状態のスクリーンショットを取得する。
- 正確な手順と観察した状態を短いメモに残す。
- 成果物は設定済みの一時成果物ディレクトリに置く。

読み取り専用のメディアレビュアーに、1 つの問いに答えさせます。その証拠は、判別力のある壊れた状態を目に見える形で示しているでしょうか。

答えが「いいえ」か「不明」なら、その再現は確認済みではありません。より良い証拠をキャプチャするか、`Could not reproduce` を使います。

詳細な証拠は、運用スレッドが設定されている場合にだけ、そこへ投稿します。ソース側の更新は簡潔に保ちます。

## 9. 再現の結果を報告する

まず運用ステータスを更新します。

`Could not reproduce` または `Blocked` のときは、ソーススレッドに何も投稿しません。結果は運用スレッドか実行出力で伝えます。

再現が確認できたときは、ソースのプリフライトを実行し、求められていないソースへの返信を最大 1 つだけ投稿します:

- 不具合が再現したと述べる。
- 運用の証拠スレッドがあれば、リンクする。
- 短い所見を最大 3 つ含める。
- トラッカーの課題があれば、リンクする。
- 既定では所有者をメンションしない。

証拠を添付するのは、設定済みの Slack アクションがそれを同じソーススレッドの中に保ち、組織の保持ポリシーが許すときだけです。

設定済みの却下ウィンドウを待ちます。人がセットアップや解釈の誤りを示したら、再現を 1 回だけ訂正します。有効な却下が無いままウィンドウが閉じるまで、修正フェーズを始めてはいけません。

## 10. 既存の修正を検証する

修正の成果物があるときは、`references/verify-existing-fix.md` に従います。

検証では、ベースラインで症状が現れ、パッチ適用後のビルドでは現れないことを示す必要があります。どちらのパスも、実際の UI を 2 回使います。

既存の修正を編集したり、競合するパッチを足したり、差し替えの pull request を開いたりしてはいけません。

## 11. 範囲を絞った修正の条件を満たす

修正を試みるのは、次のすべてが成り立つときだけです:

- 結果が、紛れのない確認済みの再現である。
- メディアのレビューが、壊れた最終状態を確認した。
- 既存の修正の成果物が現れなかった。
- 却下ウィンドウの間に、誰も修正を名乗らなかった。
- 実行時の証拠が根本原因を特定している。
- 見込みのある変更が、設定済みの修正の予算とリポジトリの範囲に収まる。
- control アダプタが、ベースラインとパッチ適用後の両方のビルドを実行できる。

条件が 1 つでも満たされなければ、再現の報告は残したまま、pull request を出さずに止まります。

ゲートを通過したら、運用ステータスを `Attempting bounded fix` に更新します。

## 12. 根本原因を特定して実装する

Slack への投稿、最終的な diff のレビュー、コミット、pull request は、すべて調整役が所有します。

読み取り専用のワーカーができること:

- コードと履歴をたどる
- テストを提案する
- 影響範囲をマッピングする
- diff をレビューする
- メディアをレビューする

編集、外部への書き込み、ステータスの投稿、修正の所有はしません。

範囲を厳密に絞ったコード編集は、ツールの分離によってそのワーカーから Slack の資格情報とすべての Slack への書き込みアクションが除かれる場合に限り、このフェーズで委任できます。そのプロンプトには、Slack への書き込みの明示的な禁止を引き続き含める必要があります。調整役はその編集をレビューし、必要なテストを実行または検証します。ツールの分離が確かでなければ、編集は調整役に残します。

仕組みを実行時の証拠で確認します。編集する前に、競合する仮説を排除します。

正当化できる最小の変更で、根本原因を修正します。

- 安価なローカルのテスト対象があれば、pstack の `tdd` スキルを呼び出し、修正の前に失敗するテストを書きます。
- そのパスが高価、不明瞭、または統合寄りで TDD を見送ったときは、その理由を述べます。
- 無関係な片付けは入れません。
- 変更が設定済みの工数またはリスクの予算を超えて大きくなるなら、止まります。

## 13. 修正を証明する

元のベースラインの証拠は保持します。

パッチ適用後のビルドで:

1. 同じ実際の UI パスを実行する。
2. それを 2 回繰り返す。
3. 壊れた状態が無くなったことを示す。
4. その代わりに期待される状態が現れることを示す。
5. 修正後の録画とスクリーンショットをキャプチャする。
6. ベースラインで使ったのと同じ実際の状態値を突き合わせる。

コンパイル、ユニットテスト、コードレビュー、もっともらしい diff は、修正後の証拠にはなりません。

焦点を絞ったテストを実行し、そのうえで変更した振る舞いの周りの影響範囲をスモークします。変更が影響しうる、近くの状態、入力、権限、プラットフォーム、失敗経路をカバーします。回帰が残るなら、pull request を出さずに止まります。

## 14. ドラフト pull request を開く

修正前後の証明が取れてからだけ:

- 最終的な diff に、無関係な変更や秘密が無いかレビューする。
- リポジトリの必須チェックを実行する。
- リポジトリのワークフローが許すなら、小さく順序立てたコミットを作る。
- ドラフト pull request を開く。このワークフローからマージやデプロイを決してしない。
- 設定済みのトラッカーの課題を、そのトラッカーが対応する pull request の構文でリンクする。
- 設定済みの公開 URL の形式、通常は `https://github.com/{owner}/{repo}/pull/{number}` を使う。
- 再現の手順、根本原因、テストの結果、修正前後の証拠、影響範囲のチェックを含める。
- pull request の本文とすべての Slack の更新を、pstack の `unslop` スキルに通す。

pull request の作成に失敗したら、成功したと主張してはいけません。コミットやブランチの状態を実行出力に残し、運用ステータスを `Fix did not land` にします。

成功したら、運用ステータスを `Draft pull request opened` にし、運用スレッドに、リンクした pull request を添えて簡潔な返信を 1 つ投稿します。ソースチャンネルに 2 つ目のルートを作ったり、求められていないソースへの返信をしたりしてはいけません。

## 15. フォローアップと片付け

設定済みの運用スレッドを、フォローアップのウィンドウ 1 つ分だけ監視します。

- 直接の質問には、すでに集めた証拠から答える。
- セットアップを無効にする訂正であれば、具体的な訂正を 1 つ適用し、再現を 1 回だけやり直す。
- 人間どうしの調整や雑談には入らない。
- 頼まれたら止まる。

常に control アダプタの片付けの機能を呼び出します。成果物は、設定済みの保持ポリシーが許す期間だけ保持します。
