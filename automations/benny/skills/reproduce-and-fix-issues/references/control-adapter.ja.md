# control アダプタの契約

Benny は、あらゆるアプリの起動のしかたや操作のしかたを知っているわけではありません。ユーザーが、対象アプリのためにこの契約を実装する control スキルかアダプタを 1 つ設定する必要があります。

そのスキル名を `control.skill_name` に設定します。

記入済みのユーザー視点の機能マップのパスを `control.feature_map_path` に設定します。コピーした例を編集するのではなく、[`feature-map.example.md`](feature-map.example.ja.md) を `.cursor/automations/benny/` の外にコピーして埋めます。

スキル、機能マップ、必須の機能のいずれかが欠けている、曖昧である、または不完全であれば、再現と修正の作業はフェイルクローズにしなければなりません。

## 必須の機能

### 起動

要求されたアプリのリビジョンを、要求されたテスト環境で起動します。

入力:

- リポジトリとリビジョン
- ビルドまたは起動のモード
- ワークスペース、アカウント、フィクスチャ、機能の状態の要件
- 成果物ディレクトリ
- 記入済みの機能マップのパス

返すもの:

- セッション識別子
- アダプタが正しいアプリと環境をどう確認したか
- 安定したアプリマーカー
- 後の呼び出しに必要な、実行中のプロセスや対象の詳細
- 欠けている機能があればその内容

アダプタは対象アプリを、似たウィンドウ、シェル、本番インスタンスと区別できなければなりません。

### UI を操作する

実際のユーザー操作を行います:

- クリック
- 入力
- キー押下
- スクロール
- ドラッグ
- リサイズ
- アプリのコントロールを使った移動

ロール、ラベル、安定したセレクタを優先します。座標は、新しく撮ったスクリーンショットの後でだけ使います。

各アクションと、観察された状態の変化を返します。

症状を作り出すために、内部状態を設定したり、隠れたアプリのメソッドを呼んだり、ストレージに直接書き込んだり、DOM の変更を注入したりしてはいけません。

### マップ済みの機能と状態を操作する

アプリを操作する前に、該当する機能マップのセクションを読みます。

アダプタは、次のための手段を提供しなければなりません:

- マップ済みのすべての機能へ、ユーザーから見えるパスで移動する。
- その機能に列挙されたアダプタのアクション名を呼び出す。
- 該当するとき、default、hover、focus-visible、active、disabled、loading、empty、error、selected、open、expanded、および機能固有の状態を操作する。
- 安全なフィクスチャデータ、権限、フラグ、サービスの応答、またはサポートされたテスト用のコントロールで、状態を整える。
- 2 回目の独立した再現の試行のために、機能をリセットする。
- 機能マップが指定するスクリーンショット、動画、読み取り専用の突き合わせをキャプチャする。

ロール、アクセシブル名、ARIA の関係、安定したコンポーネントのマーカー、用途にちなんで名付けた data 属性を使います。生成された CSS や StyleX のクラス、動的なハッシュ、子のインデックス、壊れやすい DOM の位置を決して使いません。

前提条件を整えることは、報告された症状を注入する許可ではありません。再現そのものは、あくまで実際のユーザー操作から生まれる必要があります。

### 状態を検査する

UI が示しているものを裏付けるために、状態を読みます。

例:

- アクセシビリティツリー
- DOM またはビューの階層
- プロセスの状態
- ローカルのログ
- ネットワークリクエストの状態
- アプリが公開しているデバッグ状態

検査は読み取り専用です。問い合わせが状態を変えるなら、それは `drive UI` に属し、実際のユーザー操作を表していなければなりません。

### スクリーンショット

現在のアプリの状態を、要求されたパスにキャプチャします。

返すもの:

- ファイルのパス
- キャプチャした時刻
- アプリマーカーまたはウィンドウのタイトル
- 何が写っているべきかの短い説明

スクリーンショットには、正しいアプリがテスト対象であることを証明できるだけのアプリの外枠 UI（chrome）が写っている必要があります。

### 録画

再現のパス全体を囲むように、画面録画を開始・停止します。

返すもの:

- ファイルのパス
- 開始と停止の時刻
- キャプチャしたウィンドウまたは領域
- 音声や機微なオーバーレイを除いたかどうか

録画には、セットアップや読み込み中の画面だけでなく、判別力のある最終状態が写っている必要があります。

### 片付け

アダプタが作ったプロセスとセッションを停止します。

使い捨てのものを削除します:

- ブラウザやアプリのプロファイル
- 一時ワークスペース
- アダプタが作った場合は、テスト用のアカウントやフィクスチャ
- デバッグ用のポートとトンネル
- 保持期間を過ぎたキャプチャ

何を停止し、削除し、保持し、人に残したかを返します。

片付けは、ユーザーの作業を削除してはいけません。

## アダプタの振る舞い

アダプタは次のことをしなければなりません:

- 再現が始まる前に、機能を報告する。
- 機能マップのどのセクションを操作でき、どれがブロックされているかを報告する。
- ベースラインとパッチ適用後のビルドで、同じ環境の入力を使う。
- 起動の失敗を、失敗として明示する。
- リトライを制限する。
- 秘密をログや成果物に入れない。
- キャプチャをリポジトリの外に置く。
- 2 回の再現の試行の間に、まっさらな、またはリセットされた状態をサポートする。
- ユーザーが安全なテスト用のアクションを明示的に設定した場合を除き、本番への変更を避ける。

## 環境の言い換え

環境がブロックだと宣言する前に、プラットフォーム固有の名詞を使わずに欠陥を言い直し、同じ振る舞いが使える環境で安全にテストできるかを問います。

例:

- 特定のブラウザ名は、任意の外部ブラウザを意味することがある。
- 特定のキー名は、設定済みのショートカットを意味することがある。
- 特定のリモートホスト名は、遅延した、または切断されたリモートの対象を意味することがある。

言い換えた試行を使うのは、それが同じ根底の振る舞いをテストするときだけです。それを言い換えた証拠として明示します。欠けている環境が欠陥の一部であるときは、それを正確な再現と呼んではいけません。

ハードウェアのプロンプト、OS の権限ダイアログ、デバイス専用の API、利用できないアカウントの状態は、実際のブロックになりえます。

## セットアップの確認

再現オートメーションを有効にする前に、無害なアダプタの確認を 1 回実行します:

1. アプリを起動する。
2. 安定したアプリマーカーを確認する。
3. 記入済みの機能マップのセクションを 1 つ読み込む。
4. その機能へ、ユーザーのパスを通って移動する。
5. マップ済みのアダプタのアクションを通して、使い捨ての状態を 1 つ操作する。
6. 結果の状態を検査する。
7. スクリーンショットを取得する。
8. 短いクリップを録画する。
9. 片付ける。

再現の作業を有効にするのは、9 つのステップがすべて成功し、ソースチャンネルへの Slack 投稿が関わらないときだけです。
