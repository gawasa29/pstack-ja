# 既存の修正を検証する

オープンな pull request かマージ済みのコミットがこの報告を直す可能性があるときは、このモードを使います。

既存の成果物が修正を所有しています。それを検証します。編集したり、競合するパッチを書いたり、別の pull request を開いたりしてはいけません。

## 成果物の条件を満たす

具体的な成果物を 1 つ必須にします:

- 症状に対処するコード変更を含む、オープンな pull request
- マージ済みの pull request
- コードと意図が一致する、マージ済みのコミット

スレッドでの主張、トラッカーのステータス、ブランチ名、原因の仮説は、pull request やコミットを伴わなければ足りません。

成果物が複数あるときは、ソーススレッドやトラッカーからリンクされているものを選びます。そうでなければ、影響を受けたコードに最も近いものを選び、理由を述べます。

## 作業ツリーを守る

リポジトリが対応していれば、分離したワークツリーか、別のきれいなチェックアウトを使います。ユーザーの変更を上書きしてはいけません。

記録するもの:

- ベースラインのリビジョン
- パッチ適用後のリビジョン
- pull request またはコミットの URL
- 両方の実行で共有するビルドと環境の入力

通常の `github.com` の pull request リンクを使います。

## ベースラインを測る

オープンな pull request では、そのベースブランチをベースラインにします。

マージ済みの修正では、修正の直前のリビジョンがビルドでき、古い振る舞いを表すなら、それを使います。

設定済みの control アダプタを通して:

1. ベースラインのアプリを起動する。
2. 正しいアプリと環境を確認する。
3. 報告されたパスを、実際の UI 操作で実行する。
4. 判別力のある症状を観察する。
5. リセットして繰り返す。
6. ベースラインの録画、スクリーンショット、状態の確認をキャプチャする。

ベースラインで症状が 2 回現れなければ、ベースラインはありません。修正が効いたと主張してはいけません。

## パッチ適用後のビルドを測る

pull request または修正のコミットを、同じ環境とデータでビルドして実行します。

1. 同じ UI のパスを実行する。
2. それを 2 回繰り返す。
3. 壊れた状態が無くなったことを確認する。
4. 期待される状態が現れることを確認する。
5. 修正後の録画、スクリーンショット、同じ状態の確認をキャプチャする。

コンパイルやテストで止まってはいけません。修正後の結果は、実行中のパッチ適用済みアプリから出ている必要があります。

## 結果

### 確認できた

ベースラインで 2 回再現し、パッチ適用後のビルドで 2 回解消する。

- 運用ステータスを検証済みにする。
- 成果物をリンクする。
- ソースのプリフライトの後、ソーススレッドに簡潔な返信を 1 つ投稿する。
- 修正前と修正後の結果を含める。
- pull request は開かない。

### 修正が不十分

症状が、ベースラインとパッチ適用後の両方のビルドで現れる。

- 運用ステータスを「再現済みだが未修正」にする。
- 成果物をリンクし、症状を解消しなかったと述べる。
- その実行がまだ使っていなければ、通常の確認済み再現のソース更新を投稿する。
- 競合する pull request は開かない。

### 結論が出ない

ベースラインで再現しない、パッチ適用後のアプリが動かない、または証拠が判別力のある状態を示していない。

- 成功したと主張してはいけない。
- どちら側（ベースラインかパッチ適用後か）が測れなかったかを述べる。
- 結果は運用スレッドか実行出力に残す。
- 直接の質問に答える必要がある場合を除き、ソーススレッドには何も投稿しない。

## 片付け

両方のビルドを停止し、保持ポリシーに従って一時プロファイルとキャプチャを削除し、ユーザーの作業を捨てずにリポジトリを元の状態に戻します。
