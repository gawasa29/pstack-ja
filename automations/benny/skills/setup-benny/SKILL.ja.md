# Benny をセットアップする

Benny は、pstack の中に休眠状態のオートメーションパックとして同梱されています。プラグインのマニフェストが公開するのは、pstack の通常のスキルルートだけです。このファイルと 2 つの運用ファイルはスラッシュスキルではありません。

人間は、Cursor にパックの `FOR_AGENTS.md` を指定することでセットアップに入ります。ブートストラップの流れでは、パック全体を対象リポジトリにコピーし、その後 `.cursor/automations/benny/skills/setup-benny/SKILL.md` にあるこのファイルを直接読みます。

Benny には、外部の設定と、2 つのライブな Cursor オートメーションが必要です。

ユーザーが明示的に頼むまで、オートメーションを作成・更新しないでください。秘密の値をプラグインのファイル、プロンプト、コミットする設定に書くことは決してしないでください。

## 1. パックをコピーし、共有の pstack スキルを有効にする

Benny の設定を尋ねる前、そして組み込みの `/automate` スキルを呼び出す前に、これを行ってください。

どのリポジトリでオートメーションを動かすかを尋ねてください。ソースパックは `FOR_AGENTS.md` を含むディレクトリです。宛先は `<target-repository>/.cursor/automations/benny/` です。

ソースパック全体を宛先にマージします。

1. 宛先が無ければ作成します。
2. すべてのソースファイルを、同じ相対パスにコピーします。
3. 宛先にしかないファイルは保ちます。インストールやリフレッシュの間に、無関係なファイルを削除することは決してしないでください。
4. ユーザーが所有する設定、機能マップ、ルーティングマップは、宛先の外に置きます。それらを上書きすることは決してしないでください。
5. ソースが管理するファイルが既存で内容が違うときは、diff を確認し、ローカルの編集を捨てずにマージします。所有が曖昧なら、置き換える前に止まって尋ねてください。
6. 宛先に `FOR_AGENTS.md`、このセットアップファイル、2 つの運用ファイル、それらの参照ファイル、テンプレートが含まれていることを検証します。

このファイルがすでに対象の宛先から読まれているなら、コピーは完了しているものとして扱い、続ける前に同じ検証を実行してください。

対象リポジトリの `.cursor/settings.json` に pstack を追加します。ファイルまたは `.cursor` ディレクトリが無ければ作成してください。

次のエントリを、既存の JSON または JSONC にマージします。

```json
{
	"plugins": {
		"pstack": { "enabled": true }
	}
}
```

無関係なトップレベルの設定と、他のすべてのプラグインエントリを保ってください。`plugins.pstack` がすでにある場合は、その `enabled` の値だけを変えます。ファイルが JSONC なら、コメントと有効な JSONC の構文を保ってください。編集した後にファイルを検証してください。

対象プロジェクトをリロードするか、そこをルートにした新しいエージェントを起動します。次の共有 pstack スキルがプロジェクトスコープから解決することを検証してください。

- `how`
- `why`
- `tdd`
- `unslop`
- `principle-separate-before-serializing-shared-state`
- `principle-minimize-reader-load`
- `principle-guard-the-context-window`
- `principle-sequence-verifiable-units`
- `principle-fix-root-causes`
- `principle-prove-it-works`

現在のセッションやユーザースコープのプラグインから読み込まれたスキルは数えてはなりません。このチェックは、対象リポジトリの新しいエージェントがプロジェクト設定を通じて pstack を受け取ることを示さなければなりません。

プロジェクトスコープのプラグインインストールが使えない、または共有の依存が 1 つでも解決しないなら、止まって失敗を説明してください。

Benny のファイルは `.cursor/automations/benny/` から直接読みます。そのディレクトリをプラグインのマニフェストに加えたり、その `SKILL.md` がスラッシュスキルの一覧に現れると期待したりしないでください。

どちらかのオートメーションを有効にする前に、`.cursor/settings.json`、`.cursor/automations/benny/`、参照される、秘密を含まない設定をコミットする必要があるとユーザーに伝えてください。ユーザーが頼むまで、それらをコミットしないでください。

このチェックが通ったら、ライブのオートメーションプロンプトは、コミット済みの運用ファイルを安定したリポジトリ相対パスで読んでよいです。プラグインのキャッシュパスを埋め込んだり、ファイルの内容をコピーしたりしてはなりません。

## 2. 設定を適合させる

コピーした次の例を開きます。

- `../../templates/configuration.example.yaml`
- `../reproduce-and-fix-issues/references/feature-map.example.md`

`.cursor/automations/benny/` の外に、ユーザーが所有するコピーを作ります。これらは設定ファイルであり、パックのファイルではありません。場所の例は次のとおりです。

- プロジェクトの設定。たとえば `.cursor/benny/configuration.yaml`
- プロジェクトの機能マップ。たとえば `.cursor/benny/feature-map.md`
- プロジェクトのルーティングマップ。たとえば `.cursor/benny/routing.md`
- ユーザーの設定。たとえば `~/.config/benny/configuration.yaml`
- ユーザーの機能マップ。たとえば `~/.config/benny/feature-map.md`

オートメーションが再現しうる、ユーザーに見える機能ごとに、機能マップのセクションを 1 つ埋めます。ユーザーの視点のままにしてください。実装の詳細や現在のコードパスをマップに固定しないでください。

コピーした例を編集しないでください。パックのリフレッシュは、競合のレビュー後にソースが管理するファイルを更新することがありますが、ユーザーが所有するコピーには決して触れてはなりません。

オートメーションが新しく行うチェックアウトが読む必要がある場合は、対象リポジトリにある、コミット済みで秘密を含まないファイルを優先してください。そうでなければ、必要な値をライブのプロンプトに言い換えて入れます。リポジトリのファイルを参照するのは、組み込みの `/automate` スキルが、そのファイルがオートメーションを動かすリポジトリにコミット済みだと確認した後だけにしてください。

コミットするパックと設定ファイルには、安定したリポジトリ相対パスを使ってください。ライブのオートメーションから、プラグインのソースディレクトリやプラグインのキャッシュパスを参照することは決してしないでください。

## 3. 必須の選択肢を埋める

次の項目を尋ねるか確認します。

- ソースの Slack チャンネル ID
- 任意の運用チャンネルまたはステータスチャンネル ID
- リポジトリの URL と既定ブランチ
- トリアージの身元または Slack ユーザー ID
- 課題トラッカーの種類、チーム、プロジェクト、ラベル、受け入れステータス
- トラッカーアダプタのスキルまたは MCP アクション
- 任意のルーティングマップのパス
- 必須の control スキル名
- 必須のユーザー向け機能マップのパス
- ステータスの絵文字文字列
- pull request の URL 形式
- ポーリングと作業量の予算
- トリアージ、再現、コード作業、メディアレビュー用のモデルスラッグ

ユーザーの Cursor モデルピッカーやサポートされるモデル一覧で利用可能として示されているモデルスラッグだけを使ってください。スラッグを推測しないでください。非公開の既定値を持ち込まないでください。

ソースチャンネル、トリアージの身元、リポジトリ、トラッカーアダプタ、control スキル、機能マップは明示されていなければなりません。必須の値が 1 つでも曖昧なままなら、セットアップを失敗させてください。

保存する前に、最終的なオートメーションの名前、説明、プロンプトのシム（prompt shim）に、pstack の `unslop` スキルを適用してください。

## 4. 連携の能力を確認する

トリアージのオートメーションには、次が必要です。

- 設定したソースの Slack チャンネルとそのスレッドへの読み取りアクセス
- そのチャンネルでのスレッド返信アクセス
- 報告にメディアが含まれる場合の、添付のメタデータとファイルのダウンロードアクセス
- 設定した課題トラッカーアダプタを通じた、検索、読み取り、作成、更新のアクセス

再現のオートメーションには、次が必要です。

- ソーススレッドへの読み取りアクセス
- ソースチャンネルでのスレッド返信アクセス
- 設定した運用チャンネルでの、任意の投稿と編集のアクセス
- リポジトリの読み取りと履歴へのアクセス
- ドラフトの pull request を開ける pull request アクション
- 設定した control アダプタのスキル

読み取りと投稿には、設定した Cursor の Slack アクションを優先してください。任意の `BENNY_SLACK_BOT_TOKEN` は、運用ステータスのメッセージを 1 つ編集する、添付をダウンロードする、といった狭い隙間を埋めるのに使ってよいです。値はシークレットマネージャか環境に置き、YAML には置かないでください。

文書化されていない連携エンドポイントを使わないでください。

## 5. ルーティングマップを用意する

ユーザーが別ルートへの転送（reroute）やオーナーへの ping を望む場合は、次の手順で行います。

1. `../triage-issue-reports/references/routing.example.md` を `.cursor/automations/benny/` の外にコピーします。
2. すべてのプレースホルダーを、公開された値か組織内の値に置き換えます。
3. オーナーへの ping は既定でオフのままにします。
4. ping を許すのは、設定済みの機能オーナーか、回帰の原因である可能性が確認された作者に対してだけです。

ルーティングマップが設定されていない場合、トリアージは報告を分類してよいですが、宛先やオーナーを推測してはなりません。

## 6. control アダプタを検証する

`../reproduce-and-fix-issues/references/control-adapter.md` と、ユーザーが完成させた機能マップを読みます。

指名されたスキルが次を行えることを確認します。

- 対象アプリを起動できます
- マップされたすべての機能を、実際の UI を通してたどれます
- マップされた状態を、宣言されたアダプタのアクションを通して動かせます
- 結果を強制せずに状態を調べられます
- スクリーンショットを取得できます
- 録画を開始・停止できます
- 自分のプロセスと一時データを後始末できます

能力が 1 つでも欠けているなら、再現のオートメーションは無効のままにしてください。実行していない再現を主張するのではなく、フェイルクローズ（fail closed）しなければなりません。

## 7. ライブのオートメーションを用意する

初回の作成なのか、既存のオートメーションの設定なのかを尋ねます。

どちらの道でも、コピーしたパックの `../../FOR_AGENTS.md` を、ユーザーの意図の主たる情報源として読みます。2 つのトリガー、ツール、指示、成果、共有ルールを理解するために使ってください。

### 初回の作成

オートメーションは 1 つずつ作成します。

各オートメーションについて、次の手順を実行します。

1. 一致する、コピーしたプロンプトテンプレートを、二次的な内部の素材として読みます。
2. `FOR_AGENTS.md`、完成した Benny の設定、テンプレートの意図を、完全な自然言語の依頼に変えます。
3. ライブのプロンプトに、`.cursor/automations/benny/` の下にある、対応するコミット済みの運用ファイルを読んで従うよう指示します。
4. プラグインのソースやキャッシュのパスではなく、安定したリポジトリ相対パスを使ってください。運用ファイルの内容をライブのプロンプトにコピーしないでください。
5. 組み込みの `automate` スキルを読んで従います。
6. `automate` に Slack チャンネル、リポジトリ、接続済みの連携を見つけさせます。
7. `automate` に、コピーしたパックと参照される設定ファイルが、オートメーションを動かすのと同じリポジトリにコミット済みであることを確認させます。
8. `automate` に、ドラフトの表を示し、承認を得て、準備状況を尋ね、Automations エディタを開かせます。
9. 次のオートメーションを始める前に、このオートメーションのエディタへの引き渡しを終えます。

次の完全なトリアージの意図を、設定から埋めて `automate` に渡します。

- 名前は `benny-triage` にします。
- 毎回の実行で `.cursor/automations/benny/skills/triage-issue-reports/SKILL.md` を読んで従います。
- 設定したソースの Slack チャンネルで、新しいトップレベルの報告それぞれをトリガーにします。
- トリガーになったスレッドを読み、その中にだけ返信します。
- 設定した課題トラッカーの連携を使います。
- 分類し、証拠（evidence）を調べ、原因をたどり、重複を排除し、明確に新規の不具合だけを作成します。
- スレッド内だけの判定 1 つを、設定した `[benny:bug]`、`[benny:performance]`、`[benny:other]` の印と、任意のトラッカー URL で終えます。
- ソースチャンネルにルートメッセージを投稿しては決してなりません。

トリアージのエディタへの引き渡しが終わったら、次の完全な再現と修正の意図を `automate` に渡します。

- 名前は `benny-reproduce` にします。
- 毎回の実行で `.cursor/automations/benny/skills/reproduce-and-fix-issues/SKILL.md` を読んで従います。
- 設定したソースの Slack チャンネルで、同じ新しいトップレベルの報告をトリガーにします。
- 設定したリポジトリと既定ブランチを使います。
- ソーススレッドを読み、その中にだけ返信します。
- pull request の作成と、設定したトラッカー、control アダプタ、機能マップの要件を含めます。`automate` が同じリポジトリにある適格なコミット済みファイルを確認しない限り、マップされたユーザーの経路と状態は言い換えます。
- 行動する前に、信頼できるトリアージの印を待ちます。
- マップされた実際の UI を通して、正確な症状を 2 回再現し、証拠を取得します。
- 既存の修正は、上書きして書かずに検証します。
- 再現が確認できた後にだけ、範囲を限定した修正を任意で 1 回試み、証明とチェックが通ったときにドラフトの pull request を開きます。
- ソースチャンネルにルートメッセージを投稿しては決してなりません。

`automate` の Slack、リポジトリ、連携、完全性、認証、ドラフトのレビュー、承認、準備状況、エディタへの引き渡しの仕事を重複させないでください。

### 既存のオートメーション

組み込みの `automate` スキルは作成専用です。既存のオートメーションを探したり、調べたり、更新したりするのに使わないでください。

設定、ルーティング、control アダプタ、機能マップの検証を終えます。そのうえで、次の簡潔なエディタのチェックリストをユーザーに渡してください。

既存のトリアージのオートメーションでは、次を更新します。

- 名前と説明
- `.cursor/automations/benny/skills/triage-issue-reports/SKILL.md` を読むよう直接指示する項目
- 新しいトップレベルの Slack 報告のトリガーとソースチャンネル
- Slack スレッドの読み取りと返信の能力
- 課題トラッカーの連携
- 言い換えたトリアージの指示、スレッド内だけのルール、Benny の判定の印

既存の再現のオートメーションでは、次を更新します。

- 名前と説明
- `.cursor/automations/benny/skills/reproduce-and-fix-issues/SKILL.md` を読むよう直接指示する項目
- 対応する Slack のトリガーとソースチャンネル
- リポジトリと既定ブランチ
- Slack スレッドの読み取りと返信の能力
- pull request アクション
- トラッカー、control アダプタ、機能マップの要件
- 印の待機、証拠、検証、範囲を限定した修正についての、言い換えた指示

既存の各オートメーションは、その Automations エディタで直接更新するようユーザーに頼んでください。置き換えや重複を作らないでください。

### 作成の境界

オートメーションのバックエンドサービスやバックエンドのオートメーションツールを直接呼び出すことは決してしないでください。ドラフトのフィールドを運ぶブラウザ URL を使うことは決してしないでください。Cursor のプロトコルのディープリンクを組み立てたり開いたりすることは決してしないでください。新しいオートメーションでは、唯一の完了経路は、組み込みの `automate` スキルによる、レビュー済みの Automations エディタへの引き渡しです。

エディタの保存後にスレッド安全性のテストが通るまで、どちらのオートメーションも有効にしないでください。

## 8. スレッドの安全性をテストする

テスト用のチャンネルか、無害なテストの報告を使ってください。

テストの前に、対象リポジトリの `.cursor/settings.json`、`.cursor/automations/benny/`、参照される、秘密を含まないすべての設定ファイルが、オートメーションのチェックアウトが使うブランチにコミット済みであることを確認してください。両方のライブのプロンプトが、対応するコミット済みの運用ファイルを指していることも確認してください。チェックが 1 つでも失敗したら止まってください。オートメーションはまだ有効にできないとユーザーに伝えてください。

次を検証してください。

1. トリアージがルートの `thread_ts` を保存し、判定を返信としてちょうど 1 つ投稿します。
2. 判定に、設定した印が 1 つ含まれます。
3. 再現は、設定したトリアージの身元からの印だけを受け入れます。
4. 再現が、同じ不変のソース座標を保ちます。
5. ソースチャンネルにルートメッセージが現れません。
6. 委任されたワーカーが、Slack のあらゆる書き込みアクションを使えません。
7. 座標の欠落、親メッセージの削除、プリフライトの失敗のいずれでも、投稿もトラッカーの課題も生まれません。

7 つのチェックがすべて通った後でだけ、通常のトラフィックを有効にしてください。
