# pstack をセットアップする

このページでは、プラグインをインストールし、pstack が使うモデルを選び、最初のタスクを実行します。セットアップはコマンド 1 つと短い会話だけです。

## プラグインをインストールする

Cursor のチャットで次を実行します。

```text
/add-plugin pstack
```

Cursor がプラグインのインストールを確認します。

Claude Code では、`/plugin marketplace add cursor/plugins` を実行してから `/plugin install pstack@cursor-plugins` を実行します。Claude Code はプラグインのコマンドに接頭辞を付けるため、このガイドの各コマンドはそちらでは `pstack:` を付けた形になります。たとえば `/pstack:setup-pstack` で、モデルのルールを `~/.claude/rules/pstack-models.md` に書き出します。その他の違いは [Claude Code アダプター](../harness/claude-code.ja.md) で説明しています。

## 使うモデルを選ぶ

次を実行します。

```text
/setup-pstack
```

[`/setup-pstack`](../../skills/setup-pstack/SKILL.ja.md) は、アクセスできるモデルを検出し、推論の予算（reasoning budget）を尋ね、各ロール（コード委任、判断、レビューパネル）を提示して、どうしたいかを聞きます。質問に答えてください。`~/.cursor/rules/pstack-models.mdc` に、すべての pstack スキルが読む小さなルールを書き出します。

デフォルトでは推論が `xhigh` で、これは `large` の予算と同じです。`unlimited` は各モデルをその最上位まで引き上げ、上限は `max` です。Opus は `max` になります。Grok は `xhigh` が上限なので、`xhigh` のままです。`medium` と `small` は推論を下げ、消費するトークンを減らします。

上書きするのは、気にするロールだけです。ルールに行のないロールはスキルのデフォルトのままです。デフォルトに戻すには、そのロールの行を削除します。`/setup-pstack` を再実行すると、モデルがデフォルトと異なるロールはそのまま維持されます。デフォルトが変わると、変更前に書いたルールは古いデフォルトを固定したままなので、そのロールの行を削除するか、ファイルを削除してから、もう一度 `/setup-pstack` を実行してください。

Auto を使うとどうなるのか気になるかもしれません。ロールを `inherit-parent` か `auto` にすると、pstack はサブエージェントの `model` フィールドを省略するので、サブエージェントは親チャットのモデルを継承します。どちらの値も意味は同じで、どちらもモデルのスラッグではありません。パネルのロールでは値はリストで、1 エントリにつき 1 つのサブエージェントが動くため、リストの長さがパネルの大きさになります。セットアップでは `swarm workers` も設定します。これは、レースが各アームにモデルを指定しない限り、すべての `/swarm` ワーカーが使うデフォルトのモデルです。

## 検証スキルの提案を受け入れる（受け入れなくてもよい）

セットアップの最後に、`/setup-pstack` はプロジェクト内でアプリの動作を証明する手段を探します。`verify-*` スキルか、既存のハーネスのどちらかです。どちらも見つからない場合、[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.ja.md) で生成するよう一度だけ提案します。

はいと答えると、`.cursor/skills/verify-<app>/` を書き出します。これは、ユーザーと同じようにアプリを操作する方法をエージェントに教える、プロジェクトローカルのスキルです。引き渡す前に、スキルが動くことを一度証明します。いいえと答えると、セットアップは先に進みます。`/create-verification-skill` はいつでも自分で実行できます。詳しくは [検証して出荷する](06-verify-and-ship.ja.md) で扱います。

pstack が初めてなら、はいと答えてください。自分の作業を確認できるエージェントは、確認が通るまで進み続けます。確認できないエージェントは、結果をすべてあなたに返して手で確認してもらうことになります。このガイドの中で、最も元が取れるのは検証スキルです。

続いてセットアップは、プロジェクトにまだ無ければ、[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.ja.md) で形式検証スキルを生成するよう一度だけ提案します。テストは、誰かが書こうと思ったケースを確認します。形式検証スキルは、コードの重要な性質を 1 つ、たとえば「ジョブが同時に 2 回走ることはない」を、宣言した範囲内のすべてのケースで確認します。コードに並行処理、リトライ、ステートマシン、パーサーがあるなら、はいと答えてください。そうした領域ではバグの代償が大きく、テストが壊れるケースまで届くことはほとんどありません。そうでなければいいえと答え、状況が変わったら後で実行してください。詳しくは [検証して出荷する](06-verify-and-ship.ja.md) で扱います。

セットアップが終わったら、新しいチャットを開始してください。モデルのルールは新しいセッションから適用されます。

## コストを抑える

pstack はサブエージェントとレビューパネルに余分なトークンを使います。それが厳密さの代償です。消費を減らすには:

- `/setup-pstack` を再実行し、より小さい推論予算か、より安いモデルを選びます。メインチャットには強いモデル、コードのロールには安くて速いモデル、という分担が良いバランスです。
- ロールを `auto` か `inherit-parent` にすると、そのチャット自身のモデルで動きます。
- パネルのリストを短くします。1 エントリにつき 1 つのサブエージェントが動きます。
- `/poteto-mode` は厳密さが要る作業のために取っておきます。小さくて明らかな編集には要りません。

## 最初のタスクを実行する

現実的で小さなものを選び、同僚に説明するときと同じように伝えてください:

```text
/poteto-mode add a --json flag to this command. text output stays byte-identical. verify both.
```

todo リストを見てください。最初の項目は、マッチしたプレイブックの手順をコピーしたものです。このプロンプトなら Feature プレイブックです。`/poteto-mode` が手順をスキップした場合、その手順は `skip: <reason>` 付きでリストに残るので、何をやらないと決めたかが分かります。

ここからは普通に追加の指示を入力できます。`/poteto-mode` をチャット全体で有効にしておくには、`/` メニューから Enter ではなく Option+Enter（Mac）または Alt+Enter（Windows）で選びます。すると [カスタムモード](https://cursor.com/docs/skills#using-a-skill-as-a-custom-mode) になり、終了するまで毎ターンコンテキストに残ります。カスタムモードは Agents Window と CLI で使えます。単なる Enter はスキルを 1 つのメッセージに紐付けるだけで、チャットが進むと薄れていきます。
