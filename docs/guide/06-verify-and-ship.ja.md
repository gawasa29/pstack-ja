# 結果を検証して PR を開く

「コンパイルが通る」は証拠になりません。[Prove It Works](../../skills/principle-prove-it-works/SKILL.ja.md) は、成功を報告する前に本物の成果物を確かめるようエージェントに求めます。あなたの仕事は、その「本物の成果物」を確かめられるようにすることです。このページでは、完了条件の書き方、計測値の吟味、アプリ用の検証スキルの生成、テストがほとんど届かない性質の形式検証、PR を開くところ、そしてマージまで導くところを扱います。

検証は、エージェントの作業でいちばん遅いステップです。ふつうは人間を待つステップだからです。エージェントが自分で検証できるようにすれば、ボトルネックはあなたでなくなります。ここを飛ばすと、エージェントを増やしても、レビューしていない未検証の作業が増えるだけです。

![試作機が本物のテストコースを飛んでいる。誰かがストップウォッチでその時間を計り、ロボットたちが飛行を撮影してチェックリストを埋めている。ターミナルには verify: pass、evidence: captured と表示されている。](./images/verification.jpg)

## 完了条件を先に書く

「完了」が何を意味するかを、最初のプロンプトに、しっくりくる言葉で書きます。

```text
/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
```

これでエージェントは、あなたの気分を推し量るのではなく、実行できる3つのチェックを持ちました。返答が来たら、正確なコマンドと出力が添えられているはずです。チェックを実行できなかったなら、よい返答は「inconclusive（判定不能）」と言います。証拠のない自信満々の返答は危険信号です。

チェックは変更に合わせます。

- CLI の変更なら、本物のコマンドを実行します。
- UI の変更なら、起動中のアプリで変更したフローを歩きます。参照とピクセル単位で一致させる必要があるなら、[Visual parity プレイブック](../../skills/poteto-mode/playbooks/visual-parity.ja.md) がスクリーンショットを凍結したベースラインと diff し、目視で判断しません。
- パーサーや移行なら、保存済みの入力を再生します。
- パフォーマンスの変更なら、前後のプロファイルを比較します。
- ストレージの変更なら、書いた値を読み返します。

証拠は、自分で確かめられる成果物として求めてください。失敗するテストと、そのあとに通るテスト。ビフォーアフターの動画。トレース。スクリーンショット。修正がすでにマージ済みなら、main で同じチェックをもう一度やってもらいます。もっともらしい説明より成果物のほうが勝ります。実行全体を再生しなくても、反論できるからです。

完全には信じていない小さな diff なら、[`/blast-radius`](../../skills/blast-radius/SKILL.ja.md) が他所で壊しうるものを探します。変更を安全にするたった1つの事実を見つけ、その事実を、論じるのではなくコードを動かして証明します。

## `/benchmark-checklist` で計測値を吟味する

ビフォーアフターの数値は、うっかり間違えやすい証拠の筆頭です。温まったキャッシュ、片側だけのデバッグビルド、計測区間の中で一度も走っていない処理。どれも説得力のある高速化を生み出してしまいます。数値を報告したり、それに基づいて動いたりする前に、こう打ちます。

```text
/benchmark-checklist vet the export speedup before it goes in the pr
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.ja.md) は7つの問いを投げ、それぞれについて実行からの証拠を求めます。

1. この数値を律しているのは何で、なぜ2倍になっていないのか。
2. どの側も、本番と同じ設定でチューニングされて走ったか。
3. 結果が、ディスク帯域やコア数といった物理的な限界を破っていないか。
4. 何かがエラーになったり、誤った出力を返したりしていないか。
5. 交互に実行しても再現するか。中央値と範囲はあるか。
6. ユーザーが待つパス上で、エンドツーエンドで意味があるか。
7. その処理は本当に計測区間の中で起きていたか。

判定は、faster、slower、no measurable difference、inconclusive のいずれかで返り、実行回数、範囲、リミッターが添えられます。リミッターを名指しできないとき、または片側がチューニングされずに走ったときは、inconclusive と言います。`/poteto-mode` は Perf issue と Hillclimb のプレイブックの中でこのチェックリストをすでに実行するので、自分で打つのは、それらの外で何かを計測したときや、他人の数値がよすぎるように見えるときです。これは [Explain the Number](../../skills/principle-explain-the-number/SKILL.ja.md) という原則の実用形です。

## プロジェクトの検証スキルを作る

上の UI の項目には、実際の要件が隠れています。エージェントには、あなたのアプリを動かすスクリプト化された手段が必要です。プロジェクトにすでにあるなら万々歳です。ないなら、これを実行します。

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.ja.md) は、あなたではなくリポジトリにインタビューします。ユーザーが触るもの、アプリがローカルでどう起動するか、何で動かせるか（まず既存のハーネス、なければブラウザと CDP、PTY、あるいは素の HTTP）、どんな証拠が振る舞いを証明するか、2つのインスタンスを並べて動かせるか、を突き止めます。あなたに聞くのは、コードからは答えられないことだけです。

`.cursor/skills/verify-<app>/` を書き出します。エージェント向けの指示で、Launch、Doctor、Drive、Evidence、Cleanup の各セクションを正確に備え、同梱するスクリプトがあれば Helpers セクションを、さらに `features/` の下にフィーチャーマップを置きます。フィーチャーマップは、アプリが何をするかと、どの結果が各機能の動作を証明するかを索引化したものです。このスキルには [worked feature-map example](../../skills/create-verification-skill/references/feature-map-example/) が同梱されていて、README の索引と、必須の H2 を4つ使った機能ごとのファイルが入っています。引き渡す前に、生成器はスキルを一度エンドツーエンドで証明します。起動し、doctor チェックを走らせ、機能を1つ動かし、証拠を記録し、片付け、そして片付けのあとも証拠が残っていることを確かめます。この証明が失敗したら、その出力は使わないでください。

それ以降、「アプリで検証して」は、このリポジトリでどのエージェントも実行できる手順になります。セットアップの会話は要りません。証拠を特定の形で欲しいときは、プロンプトでそのスキルを名指しします。

```text
/poteto-mode build the bulk-archive action. use /verify-<app> to verify your changes and show me a video and screenshots as proof.
```

```text
/poteto-mode repro this with /verify-<app>. if it repros on main, fix it and show me a video as proof.
```

検証スキルが動くようになったら、[`/swarm`](../../skills/swarm/SKILL.ja.md) が一通りのパスをフィーチャーマップの項目ごとに分割し、結果を集約できます。検証役の swarm は、十分大きなサンプルでパフォーマンス改善を裏付けたり、PR を出荷する前にアプリをファジングしてリグレッションを探したりもできます。

検証スキルは一度きりのものではなく、インフラとして扱ってください。コミットして、チームの全員と全エージェントが同じやり方でアプリを動かせるようにします。次は [build the lever](../../skills/principle-build-the-lever/SKILL.ja.md) です。エージェントがアプリをクリックして回る使い捨てスクリプトを書き続けるなら、代わりにスキルが呼ぶ小さな制御用 CLI を頼んでください。エージェントのトークン消費が減り、どの実行も再現可能になります。エージェントがうまく使える CLI には、次の特徴があります。

- 多数の薄いコマンドではなく、実際の仕事をする少数の合成可能なコマンド。
- 破壊的なものすべてに `--dry-run` オプション。
- 機能を一度にすべてではなく、段階的に見せるサブコマンド。
- 代わりに何をすべきかを言うエラーメッセージ。
- 充実した `--help` テキスト。
- JSON などの機械可読な出力。

ついでに、開発環境のセットアップも再現可能にしてください。シードデータ、テストユーザー、そして毎回同じやり方で環境を立ち上げる1つのコマンドです。

## 検証スキルを正直に保つ

アプリは変わりますし、フィーチャーマップは古くなります。これを少なくとも1日1回、できれば誰も覚えておかなくて済むようスケジュールされた自動化から実行してください。

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.ja.md) は生成されたスキルを監査します。機能ごとに読み取り専用のソースリーダーを並行して走らせ、そのあとマップされた全機能を動かすライブパスを1回実行します。終わり方はちょうど3つのうちの1つです。`clean` は完全なカバレッジで、出荷するものが何もないという意味です。`changed` は、証明済みの修正を1つの PR にまとめたという意味で、検証スキル自身のディレクトリに限定されます。`blocked` はブロッカーを名指しします。製品コードを編集することは決してありません。ライブパスが製品のリグレッションを捕まえたら、ドキュメントの編集で隠すのではなく、リグレッションとして報告します。

## 形式検証スキルで性質を証明する

検証スキルは、あなたが通すパスを証明します。なかには誰も通らないパスに住むバグもあります。重なり合う2つのリトライ、書き込みの途中で期限切れになるロック、順序が入れ替わって届く状態変化。テストがそうしたケースに届くことはまれです。そうしたバグが高くつくコードでは、これを実行します。

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.ja.md) はコードから対象を選びます。コードがしている約束のうち、破るとユーザーに害があり、テストがそれを壊すケースにほとんど届かないものです。検証しやすい対象ではなく、いちばん強い対象を選びます。代わりに領域やバグを名指しして、そこから始めることもできます。

```text
/create-formal-verification-skill the job lease and retry logic. a job must never run twice at once.
```

どんな問いかが道具を決めます。イベントが悪い順序で起こりうるかどうかは、設計の小さなモデルに対するモデル検査器が向いていて、どの言語でも TLA+ がその既定です。あらゆる入力に対してコードが正しく振る舞うかどうかは、コード上で動く検証器が向いています。あなたの言語で動く検証器がなければ、エージェントはそう告げて、関数を手書きしたモデルではなく、生成した入力で本物のコードをテストします。あらゆるサイズで成り立たなければならない性質は、証明を必要とすることがあります。どの道具をなぜ選んだかは、エージェントが教えてくれます。

検証するのは1つの性質で、その性質が壊れたバリアントのコードで失敗することを示します。一度も失敗を見ていないチェックは何も証明しないからです。現在のコードがすでにその性質を破っているなら、反例があなたのコードの言葉で、短い手順の列として返ってきます。性質は述べられたまま維持されるので、指摘は指摘のままです。頼まない限り、製品コードは変わりません。

プロジェクトローカルのスキルを書き出します。次のエージェントに、変更が検証済みのコードに触れるかどうか、1つのコマンドでチェックをどう実行するか、本物のバグとモデリングの誤りをどう見分けるかを伝えます。引き渡す前に、生成器はそのスキルに従って、性質を壊すスクラッチの変更を一度試し、チェックがそれを捕まえなければなりません。引き継ぎでは、何を検証したか、どの道具と境界で検証したか、チェックが見つけたもの、カバーしていないものを述べます。合格が保証するのはモデルか境界であって、システム全体ではありません。

このスキルは、各チェックがどのコードをカバーしているかと、そのチェックが最後にコードと一致したコミットも記録します。スキルを通さないマージやリファクタリングは、すでに消えたコードの記述に対してチェックが通り続ける状態を残しかねません。そうしたあとには、[`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.ja.md) を実行してください。コードから検証を更新し、再実行し、更新後の各チェックがなお失敗しうることを示し、それぞれの失敗が検証側のドリフトなのかコードのバグなのかを教えてくれます。

## 振る舞いをステートチャートで見せる

モデルの言葉での反例は、あなたを納得させます。その振る舞いを所有する PM やデザイナーには、自分たちの言葉で見える必要があります。こう実行します。

```text
/statechart what the user sees when they edit a note offline
```

[`/statechart`](../../skills/statechart/SKILL.ja.md) は、ユーザーが見るものを Mermaid のステートチャートとして描きます。TLA+ モデルから生成するので、絵と検証済みモデルがずれることはありません。読み手のルール（「オフラインの間に Synced を見ることはない」）が不変条件になります。チャートはルールを破る各状態に印を付け、レポートはそこへの最短経路を読み手の言葉で示します。引き渡しの前に、エージェントはバグの各経路を本物のコードで再現するので、モデリングの誤りがバグとして読み手に届くことはありません。

## PR を開く

```text
/poteto-mode open the pr. small ordered commits, evidence in the description.
```

[Opening a PR プレイブック](../../skills/poteto-mode/playbooks/opening-a-pr.ja.md) はワークツリーから作業し、作業を小さく順序立ったコミットにリベースし、diff を片付け、文章を unslop し、PR のリンクを返します。太った PR 1つより、細い PR 5つのほうが勝ります。育ち続けるブランチより、積み重ねたフォローアップのほうが勝ります。

## Babysit で PR をマージ可能まで導く

開いた PR は、すぐにブロッカーを集め始めます。チェックは落ち、レビュアーはコメントし、トランクは動きます。その目まぐるしい入れ替わりは [Babysit プレイブック](../../skills/poteto-mode/playbooks/babysit.ja.md) に任せます。

```text
/poteto-mode babysit this pr. get it green.
```

Babysit は PR を見張ります。GitHub では同梱のウォッチャーを、使えるなら Origin CLI を使います。ブロッカーは順番に処理します。コンフリクト、次にレビュースレッド、次に CI です。判明している修正はすべて1回のプッシュにまとめるので、チェックは修正のたびにではなく1回だけやり直されます。コメントのトリアージは懐疑的です。人間もボットも、本物の指摘とノイズを同じリストに並べるからです。本物の指摘には修正が入り、ノイズはスレッドに反証を貼って退けられます。状態だけを知りたいときは、小さく頼めば Babysit はループを始めずに答えます。

```text
/poteto-mode check on pr 123. anything outstanding?
```

Babysit はマージ可能になったところで止まります。すべてがグリーンでもマージはしません。マージは別の判断だからです。

## Shipping でスタックを取り込む（land）

グリーンであることは、安全であることと同じではありません。取り込む準備ができたら、そう言ってください。

```text
/poteto-mode land the stack.
```

[Shipping プレイブック](../../skills/poteto-mode/playbooks/shipping.ja.md) は、何かを起動する前に各 PR を独立に検証します。PR ごとに新しいエージェントが1体、振る舞いをライブで証明し、変更を判定するエージェントは、その変更を書いたエージェントではありません。そのうえで Shipping は、下から連続して検証済みの並びだけを、既定では GitHub 経由、CLI が使えるなら Origin 経由で1 PR ずつ取り込み、連鎖を最初に壊す PR を報告します。検証済みの PR が未検証の PR の上にある場合は待ちます。マージすると、下の隙間を引き込んでしまうからです。
