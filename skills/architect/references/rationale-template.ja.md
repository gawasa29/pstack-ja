# 根拠テンプレート

型スケッチと一緒に出荷する文章です。1 ページ。見出しは文の形（sentence case）にし、定型の決まり文句は入れません。斜体の注記は、実際の内容に置き換えてください。

## 問題（Problem）

*1 段落。何をしようとしているのか、そして既存のシステムや制約の何が、この形を自明でなくしているのか。もし[フェーズ A](../SKILL.ja.md) が、設計が守るべき制約（相互運用すべき既存の型、壊せない呼び出し側、境界をまたいでいた不変条件）を明らかにしたなら、ここで名指ししてください。読者が、あなたが見たのと同じ制約を見られるようにします。*

## 使い方（Usage: 呼び出し側の視点）

*型スケッチより先に、これを書いてください。利用者が読む README かクイックスタート、そして利用者自身のコードにある現実的な呼び出し箇所を 2、3 個示します。何を import し、何を呼び、何が返るか。[形](#shape)にある型スケッチは、ここから導かれます。両者は一致していなければなりません。ずれたときは、使い方に合わせてスケッチを直します。逆はしません。呼び出し側の体験が仕様です。型はそれに仕えるものです。*

## 形（Shape）

*推奨するアーキテクチャ。まずデータ構造。次に、データがシグネチャを通ってどう流れるか。土台となる判断を名指しします。どの不変条件が型にエンコードされているか、検証がどこにあるか、システムが意図的にやらないことは何かを述べます。インターフェースの深さを明示的に評価します。公開面が何の複雑さを隠し、何が呼び出し側に露出したままで、なぜインターフェースが必要以上に大きくないのかを述べます。各判断の背後にある原則を引用します（例: `per boundary-discipline`）。原則を言い直してはいけません。*

## 統合の判断（Synthesis decision）

*[arena](../../arena/SKILL.ja.md) が記入します。どの候補がベースになり、なぜか、他の各候補から何を取り込んだか、何を却下し、なぜかを記録します。*

## 受け入れたトレードオフ（Tradeoffs accepted）

*選んだ形が引き受けるトレードオフごとに 1 つの箇条書き。「私たちは Y と引き換えに X を受け入れます」という形で書きます。将来の読者が見落としと取り違えそうなもの、たとえば早すぎる最適化や早すぎる単純化に見えるものも、すべて名指ししてください。*

## 検討した代替案（Alternatives considered）

*必須です。具体的な代替案の形を少なくとも 1 つ挙げ、なぜ負けたかを 1 行で書きます。各代替案は、実装の単純さだけでなく、インターフェースの深さで評価します。呼び出し側に露出する複雑さと、隠す複雑さを名指しします。設計空間に本当の競合があったなら、代替案は 2、3 個が適切です。制約が答えを強いたなら 1 個でよく、結論は「これが唯一実行可能な形だった。なぜなら…」と書きます。同じ形の変種を並べるのは避けてください。この節は、選んだ形が検討して却下した設計の代替案を扱うもので、他の runner の候補ではありません。*

## 未解決の問いとリスク（Open questions and risks）

*スケッチ中に気づいた、人間が判断を下す必要のあること、実装を始める前に指摘しておく価値のあるリスク。断定ではなく問いの形で書いてください。人間の答えがコメントではなく解決になるようにします。*

## 次の実装ステップ（Next implementation step）

*スケッチに対して最初に作るもの。1 文。統合の直後（チェックポイントを選んだ場合はフェーズ D の承認後）に、すぐ書き始めるものです。*
