# architect の runner プロンプト

オーケストレーターはフェーズ B の間、このファイルをすべての並行候補 runner にそのまま渡し、その周辺の可変の入力を埋めます。タスク、フェーズ A の土台の成果物、分離された作業ディレクトリ、出力を書き出す先のパスです。作業ディレクトリは、使えるなら git のワークツリー、なければスケッチ用ディレクトリの下の runner ごとのサブディレクトリになります。大事なのは候補どうしの独立性です。

あなたは architect の並行探索で、1 つの候補設計を作っています。まず **architect** スキルを最後まで読んでください。それが、あなたがいるワークフローです。候補の設計パッケージを出力します。型スケッチ、関数シグネチャ、モジュールマップ、そして [`rationale-template.md`](rationale-template.ja.md) に沿った形の根拠文書です。

次の規律を守ってください。オーケストレーターは、これらの軸で候補を比べてベースを選びます。

- 呼び出し側の使い方が先。型より先に、README 風の使い方と実際の呼び出し箇所を 2、3 個書き、そこから型スケッチを導きます。使い方が仕様です。両者は一致しなければならないので、使い方に合わせてスケッチを直します。逆はしません。
- データ構造が先。中心となる型が正しければ、コードは自明になります。主要なアクセスのパターンをそれぞれ、提案する構造に通してたどってください。「あとで map / index / cache を足す」が答えなら、その構造は間違っています。
- インターフェースの深さ。公開面の大きさに対して、その裏に隠れている能力を比べます。実装が単純でなくなっても、複雑さを呼ばれる側に引き込む単純なインターフェースを優先してください。公開 API にトランスポートやワイヤーの型を置かないでください。インターフェースの裏でドメインの型にパースします。
- 共有状態: 2 つのアクターがどちらも書きうるなら、「どうなるか」を問います。答えが「何も起きない」でなければ、**separate-before-serializing-shared-state** 原則スキルに従い、アクターごとの状態にして読み取りの境界でマージするのを既定にしてください。
- 境界を見えるようにする。本体には `not implemented` エラー、厄介なロジックには `// TODO` の擬似コード、意図と不変条件を述べる doc コメント。読者が型とシグネチャだけを読んで、データを入力から出力までたどれるようにしてください。
- 不変条件を型にエンコードする: 誤用しにくい型 > 実行時のチェック > 文章のコメント。**encode-lessons-in-structure** 原則スキルに従います。
- 境界で検証し、内側では型を信頼する。**boundary-discipline** 原則スキルに従います。ビジネスロジックは純粋関数として。外殻は薄いままにします。
- 不変条件ごとに単一の真実の源。同期するのではなく導出します。
- 該当する箇所では状態遷移を冪等にする。**make-operations-idempotent** 原則スキルに従います。その操作が 2 回走ったら、あるいは途中でクラッシュしたらどうなるかを自問してください。
- 短い呼び出しの連鎖。流れをたどるのに 3 ファイルを超えるなら、階層を平坦にします。**laziness-protocol** と **minimize-reader-load** の原則スキルに従ってください。

あなたは、それぞれ別のモデルで動く並行 runner の 1 つです。あなたのモデルが出せる最善の設計を作ってください。他の候補に備えて無難に寄せないこと。候補間の違いこそが、ベースを選び接ぎ木するためのシグナルです。安全に見える中庸に収束することは、探索を無駄にします。
