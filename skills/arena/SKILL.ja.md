# アリーナ（Arena）

何かを起動する前に、各フェーズに 1 項目ずつ todo リストを作ります（Frame、Fan out、Cross-judge、Pick、Graft、Verify）。

## フェーズ A: 枠組み（Frame）

すべての候補が同じプロンプトを受け取るので、プロンプトが契約になります。

1. 各候補が作る成果物を述べます。
2. ルーブリックを導きます。*この*お題で成功がどう見えるかを表す、採点可能で具体的な基準を 3〜6 個作ります。これはフェーズ D で選ぶ側の道具になります。候補が見るのはお題だけです。
3. 走らせるモデル（ランナー）を選びます。`~/.cursor/rules/pstack-models.mdc` の `arena runners` 行を使います。ルールかその行がなければ、`claude-opus-5-5-xhigh` と `grok-4.7-xhigh-fast` でそれぞれ 1 つずつを既定にします。この行の `auto` か `inherit-parent` の項目は親モデルを意味するので、その項目では `model` を省略します。Task ツールが設定済みの項目を拒否したら、その枠はファミリーの既定で走らせ、そう言います。ファミリーは接頭辞で決まります。`claude-*`、そして `grok-*`（`cursor-grok-*` と `composer-*` を含む）です。拒否された `composer-*` の項目は `grok-4.7-xhigh-fast` で走らせます。そのファミリーに既定がなければ、または Task ツールがその既定を拒否したなら、エラーメッセージにある同じファミリーの最も近い有効なスラッグを使います。それがなければ、その枠を落とし、そう言います。落とした枠の結果ランナーが 2 つ未満になるなら、2 つになるまでランナーを足します。その行の項目が 1 つだけなら 1 つです。足したランナーはそれぞれ、残っているランナーのモデルで走らせます。残りがなければ `model` を省略して親モデルで走らせ、そう言います。arena が複数の設計方向を扱うときは、ランナーを増やします。判断よりも生成が支配的な作業では、同じモデルを N 回使います。各サブエージェントの推論の段と、その仕事に合った fast か標準の速度は、**poteto-mode** スキルの Subagents セクションに従って選びます。
4. 各候補に自分の出力先を与えます（可能なら git ワークツリー、そうでなければ `/tmp/arena-<slug>/candidate-<n>/`）。**separate-before-serializing-shared-state** 原則スキルに従ってください。

## フェーズ B: ファンアウト（Fan out）

N 個のサブエージェントを 1 つのメッセージで `run_in_background: true` を付けて起動します。それぞれに、お題、共有の土台（grounding）へのパス、自分の出力先、そして成果物と、検討した代替案および却下したものを挙げる短い根拠を作るよう指示します。

候補が何も出力しなければ、N-1 で進め、脱落を記録します。

## フェーズ C: クロス審査（Cross-judge）

フェーズ B の候補がすべて完了したら、`~/.cursor/rules/pstack-models.mdc` の `arena cross-judge pool` 行からモデルを 1 つ選びます。ルールかその行がなければ、`claude-opus-5-5-xhigh` と `grok-4.7-xhigh-fast` から選びます。読み取り専用の審査役サブエージェントを 1 つ起動します。審査役は決して親のファミリーからは選びません。ファミリーはフェーズ A のステップ 3 の定義に従います。別のファミリーの項目だけを、プールの順に試します。`auto` か `inherit-parent` の項目は親モデルなので、審査役になることはありません。既定のプールでは、Claude の親には `grok-4.7-xhigh-fast` が当たります。それ以外のファミリーの親には、まず `claude-opus-5-5-xhigh` が当たります。Task ツールが項目を拒否したら、エラーメッセージから同じモデルの、最も近い段か速度の有効なスラッグを使います。それがなければ次の項目に移ります。別ファミリーの項目がどれも走らなければ、既定のプールの項目のうち別ファミリーのものを同じやり方で試します。それもどれも走らなければ、審査役を飛ばし、フェーズ D で 1 人でベースを選び、そう言います。親のモデルがわからない場合は、プールの実際のスラッグをプールの順に試し、ファミリーの確認は行っていないと述べます。審査役はルーブリックと、パスのラベルで示された候補を見て、各基準を採点し、根拠付きでベースを推薦します。審査役はフェーズ D でのあなたの読み込みと並行して走ります。候補がまだ書き込んでいるうちに起動してはいけません。

## フェーズ D: ベースを選ぶ（Pick a base）

選ぶ前に、すべての候補を端から端まで読みます。全体の感触ではなく、ルーブリックの基準ごとに各候補を採点し、フェーズ C でクロス審査を走らせたならその結果と比べます。ベースについて一致していれば、その選択は裏付けられます。食い違うなら、どちらかに偏りがあるか、ルーブリックが曖昧だったかのどちらかです。決める前に両方の根拠を読みます。

将来の保守担当が、不変条件を壊さずに最も楽に拡張できるベースを選びます。2 つが互角に感じたら、Laziness Protocol に従って、境界がよりきれいな方か API がより小さい方を選びます。

## フェーズ E: 接ぎ木（Graft）

負けた候補をそれぞれもう一度たどり、ベースに移植する価値のあるものを見つけます。たいてい候補あたり 1〜2 個で、大半ではありません。接ぎ木はそれぞれ手作業で畳み込みます。**redesign-from-first-principles** 原則スキルに従い、結果が 1 つのメンタルモデルの下で一貫するようにします。機械的に貼り付けてはいけません。

候補が 1 つの形に収束したなら、それは強い一致です。そう記録し、合意された形を出荷します。接ぎ木は不要です。大きく食い違うなら、フェーズ A の指定が不足していました。食い違いを平均するのではなく、枠組みを作り直して再実行してください。

## フェーズ F: 検証（Verify）

統合した成果物は、他のあらゆる出力と同じように、**prove-it-works** 原則スキルに従って検証します。検証が arena が見落とした問題を見つけたなら、フェーズ A が間違っていたか（枠組みを作り直して再実行）、候補が捕まえていてあなたが接ぎ木を逃したか（フェーズ E に戻る）のどちらかです。上から塗りつぶして隠してはいけません。

## 出力

統合した成果物 1 つと、その横に短い統合メモ。メモには、ベースとその理由、クロス審査の判定またはフェーズ C が審査役を飛ばしたこと、各接ぎ木とその出所の候補、何をなぜ却下したか、収束や脱落があればそれ、そして検証結果を書きます。
