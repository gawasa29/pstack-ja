# 自分を自動化する（Automate me）

ユーザーの仕事の慣習を、エージェントが従うスキルに変えるためのガイド付きの流れです。出力は、その人向けに仕立てた 1 つの `-mode` スキルです（例: `jay-mode`、`priya-mode`）。

このスキルは他の 3 つを編成します。インラインの掘り起こし（ステップ 1）、Cursor 組み込みの `create-skill`（オーサリング）、**unslop** スキル（文章の規律）です。順序を決めるだけで、置き換えはしません。

## 流れ

### 0. 既存のスキルを確認する

ユーザーのハンドルに合う `.cursor/skills/**/*-mode/SKILL.md` と `~/.cursor/skills/*-mode/SKILL.md` を再帰的に探します。モードスキルはトップレベルだけでなく、個人用のカテゴリディレクトリ（`.cursor/skills/<handle>/`）にも置けます。1 つあれば、意図を `AskQuestion` で確認します（すでに "update my skill" などと言っていない限り）。

- 既存のスキルを更新する（繰り返し実行の既定）
- 新規に始める（まれ。やる前に理由を尋ねます）

更新モードは残りの流れを変えます。
- ステップ 1 は、スキルが最後に編集されてからの履歴だけを掘ります（`git log -1 --format=%cI <path>`）。
- ステップ 2 は、ゼロから何を捉えるかではなく、何が変わったか、何が足りないかを尋ねます。
- ステップ 4 は既存のファイルをその場で編集します。ユーザーが否定していないセクションは保ちます。新しい証拠のあるものは直します。新しいセクションは、本当に新しいルールのためにだけ足します。

### 1. 履歴を掘り起こす

ファンアウトの前に、アクティブなワークスペースのトランスクリプトを特定します。システムプロンプトがワークスペースの `agent-transcripts/` ディレクトリを名指しします。そのパスだけを使ってください。`~/.cursor/projects/*/` をまたいで glob しないでください。ワークスペースの境界を越え、無関係なプロジェクトのプライベートなチャットを読むことになります。

その範囲内の直近のエージェントとの会話を、繰り返し現れるパターンについて調べます。履歴のスライスをまたいで複数のサブエージェントを並列に走らせます（例: 直近 2〜4 週間を 3 つのスライスに分け、それぞれに十分な材料を持たせます）。各サブエージェントの推論の段と、fast か標準かの速度は、**poteto-mode** スキルのサブエージェントのセクションに従って、仕事に合わせて選びます。各スライスを掘るサブエージェントは、親が渡すワークスペース範囲のパスからトランスクリプトを読み、下のシグナルを探し、見たパターンを証拠のポインタ付きで短い構造化リストにして返します。狙う価値のある既定のシグナルは次のとおりです。

- 返答の好み（長さ、トーン、形式、"dumb it down" の訂正）
- 委任の習慣（サブエージェント、モデル、専用のワークフロー、並列性）
- 検証の構え（"done" の意味、単体テストかライブの再現か、レビュアー）
- コードと文章の規律（スタイル、引用する原則、lint / format のツール）
- プロセスの慣習（ワークツリー、コミット、PR、レビュー / マージのツール）
- メタな好み（作業中にスキルを直す、新しいスキルを提案する）

シグナルを昇格させる前に、スライスをまたいで照合します。2 つ以上のスライスで見えたパターンは信頼度が高いです。単独のシグナルは弱く、ふつうは捨てます。

### 2. ユーザーに直接尋ねる

掘り起こしでは、まだ出てきていない意図を取りこぼします。ゼロから入力させるのではなく、`AskQuestion` ツール（構造化された多肢選択）を使います。

形は、1 つか 2 つの質問にそれぞれ 4〜6 の選択肢、カテゴリの質問には `allow_multiple: true` です。広く始め（"Which areas matter most?"）、選ばれた領域について具体的な選択肢で深掘りします。構造化のラウンドのあと、自由記述のチャットの質問を 1 つ入れて、選択肢が外したものを拾います。

20 個の質問を投げつけないでください。

### 3. 見つかったものを束ねる

合わせたシグナルをセクションに分けます。よくあるものは次のとおりです（当てはまるものだけ使います）。

- **返答のスタイル**: 長さ、トーン、形式。
- **自律性**: 聞かずにどこまでやるか、MCP ツールの使用。
- **まず理解する**: 変更の範囲を定めたり調査したりするときに手を伸ばすスキル。
- **サブエージェント**: 既定、並列性、モデルとタスクの対応、専用のワークフロー。
- **文章 / コードの規律**: 原則、lint のツール、スタイルガイド。
- **レビューと検証**: 再現の構え、検証スキル、ライブテストのツール。
- **プロセス**: git ワークツリー、コミット、PR、レビュー / マージのツール。
- **スキル**: スキルを書く習慣、まずスキルを直す、新しいスキルの提案。

**poteto-mode** スキルが形を示します。粒度はそれを読んでください。中身はコピーしないでください。ユーザーのルールは poteto-mode のルールと同じではありません。

### 4. スキルの下書きを作る

Cursor 組み込みの `create-skill` スキルで、スキルを書きます。置き場所は次のとおりです。

- パス: 既存のモードスキルのカテゴリを保ちます。新しいモードなら、そのハンドルについて個人用カテゴリの慣習があるリポジトリでは `.cursor/skills/<handle>/<handle>-mode/SKILL.md` を使います。なければ、プロジェクトの `.cursor/skills/<handle>-mode/SKILL.md` を既定にします（個人用スキルを望むなら `~/.cursor/skills/<handle>-mode/`）。
- ハンドル: ユーザーの名前か、選んだ識別子。
- frontmatter の `description`: ユーザーの名前 + `/<handle>-mode` + "work in their style" で発火させ、"write code" や "review PR" のような汎用のキーワードでは発火させません。
- frontmatter の書式: `create-skill` の YAML ルールに従います。`description` は 1 つの YAML スカラーに保ちます。句読点や折り返しの都合で必要なら、引用するか、`description: >-` とインデントした継続行を使います。
- frontmatter の `disable-model-invocation: true` を既定にします。ユーザーが自分のモードを毎ターン適用したいと明示したときだけ外します。

### 5. 文章を反復する

すべての行に **unslop** スキルと `create-skill` の文章ガイドラインを適用します。

下書きをユーザーに見せ、フィードバックを受けます。複数回の反復を想定します。容赦なく削ります。モードスキルはマニュアルではありません。

### 6. 取り込む（land）

main から切ったワークツリーで作業します。コミットして PR を開きます。main へ直接 push してはいけません。

## ガードレール

- **1 つの会話に過剰適合しない。** 一度言われ、別のときには否定された好みはノイズです。成文化する前に複数の事例を要求します。
- **小賢しくしない。** 他のスキルの中身を言い直したり、メタファーを発明したり、エージェントの読み手向けに「詩的」な文章を書いたりするのは、利益のないコストです。運用可能なままにします。
- **インラインせず参照する。** ユーザーが頼りにしている他のスキルは、抜粋を貼るのではなくパスの参照として現れさせます。他所で保守している原則のドキュメントも同じです。
- **セクションは最小限に。** セクションを足すのは、そこにユーザー固有の、既定ではないルールがあるときだけです。「明確に伝える」はセクションになりません。「段落は短く。選択肢を比べるときは表。項目が本当に並列なときだけ箇条書き。」はなります。
- **慣習には一般的な名前を付ける。** 命令文では「そのユーザー」「人間」を使い、作者の名前は使いません。
- **対称性を強制しない。** 書き残す価値のあるプロセスのルールがないなら、Process セクションは丸ごと飛ばします。

## 評価

`-mode` スキルは主観的な出力です。`create-skill` 式の test / iterate のベンチマークループは、ここでは役に立ちません。ユーザーと一緒に肌感で確かめます。その人のように読めるか。何か取りこぼしていないか。それから出荷します。

description の最適化ループを回すのは、スキルの発火の精度が実際に問題になったときだけです。

## 使わない場面

- ユーザーがタスク固有のスキル（仕事の慣習ではない）を望んでいる: `create-skill` だけでよく、掘り起こしは要りません。
- 狭い 1 つのワークフローを捉えたい（例: "how I write commit messages"）。それは通常のスキルで、モードスキルではありません。
