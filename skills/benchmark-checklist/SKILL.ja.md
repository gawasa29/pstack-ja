# ベンチマークのチェックリスト（Benchmark checklist）

性能の数字を出すときに使います。PR の before と after、退行の主張、ヒルクライム（hillclimb）のハーネス、ライブラリや設定の選択などです。各問いには、コードについての推測ではなく、実行から得た証拠で答えます。

ユーザーが求めた簡単な概算なら、1 回の実行で十分です。それでも問い 4 と 7 は確認し、1 回の実行だと述べます。その実行がおかしく見えない限り、残りは飛ばします。選択肢の間の選択は、決して概算では済みません。

## 何かを実行する前に

- 出荷するつもりの言葉で、言うつもりの主張を書き留めます（「60k 行のデータセットで、書き出しが p50 で 30% 速い」）。問いは、その 1 文を試します。
- 計測スクリプトを読みます。何を計時し、何を数え、何を無視しているかに注意します。
- `uptime` でロードアベレージを、`nproc` でコア数を確認します。マシンが忙しければ、何が動いているかを突き止めます。止められないなら、両側が同じノイズを見るように交互に実行し、レポートにそう書きます。

## 問い

1. **なぜ倍にならないのか。** リミッタを名指しします。プロファイラとトレーサは作業を遅くするので、プロファイルは報告しない実行で取ります。プロセスごとの CPU（`top`、`pidstat`）、ランタイムのプロファイラ（`node --cpu-prof`、`py-spy`、`perf`）、I/O 待ち、システムコール回数（Linux なら `strace -c`）を使い、ホットスポットをソースに対応づけます。負荷生成器にも注意します。負荷生成器が先に飽和したなら、測ったのは負荷生成器です。変更しても数字が動かなかったなら、リミッタがその理由を説明します。だから、その変更を無意味と呼ぶ前にリミッタを見つけます。
2. **チューニングされていたか。** すべての側を、本番が動かすやり方で動かします。リリースビルド、本番のフラグと環境変数、バッチとトランザクションの設定、コネクションプール、本番が見るのと同じ温かさか冷たさのキャッシュ、同じバージョンと同じデータです。片側が既定のままだと、比べたのは実装ではなく設定です。リミッタが設定である場合（1 行ごとの commit、デバッグビルド、欠けたインデックス）は、その側はチューニングされていません。チューニングして測り直してから勝者を選びます。チューニングできないなら、その実行から勝者を選んではいけません。ユーザーが何を採用するかを選んでいるときは、今日出荷されるコードに主張を狭めても解決しません。ユーザーが採用するのは選択肢であって、今日の設定ではないからです。
3. **限界を超えていないか。** 計算します。秒あたりのバイト数をディスクとネットワークの帯域と、秒あたりの操作数×操作あたりのコストをコア数と、節約した時間を変更した部分がかけていた時間と比べます。実行の 10% を占める部分を取り除いても、実行はせいぜい 11% ほどしか速くなりません。限界を超えた結果は、キャッシュ、no-op、バグなど、作業とは別のものを測っています。
4. **エラーが出ていないか。** 失敗と成功以外のレスポンスを数え、出力が存在するだけでなく正しいかを確認します。拒否はたいてい速く、タイムアウトとリトライは遅いからです。スクリプトがエラーを数えていなければ、数える処理を足します。
5. **再現するか。** 各側を少なくとも 5 回、交互に（A、B、A、B……）実行し、ウォームアップ、遅延初期化、キャッシュ、ドリフトがどちらにも有利に働かないようにします。中央値と範囲を報告します。実行間のばらつきより小さい差は、測定可能な差ではありません。判断が僅差なら、順位和検定かハーネス自身の統計を使います。
6. **意味があるか。** マイクロの結果には必ず、ユーザーが待つエンドツーエンドの経路を、現実的なデータサイズと並行度で測って並べ、マイクロの結果を全体に占める割合として報告します。リクエストの 1% を占めるヘルパーは、どれだけ速くなってもリクエストをせいぜい 1% しか速くできません。
7. **そもそも起きたのか。** 作業が計時の範囲内で走ったことを確認します。リクエストがサーバーに届き、行が書かれ、バイトが読まれ、コードがその結果を使ったかです。遅延するコード（誰も反復しないジェネレータ、誰も await しない promise、JIT が捨てられる結果）とタイムアウトは、起きなかった作業の数字を生みます。

## 報告

- 判定から始めます。速くなった、遅くなった、測定可能な差はない、判断できない、のいずれかです。
- 数字は単位、実行回数、範囲、リミッタと一緒に出します。たとえば「p50 41 ms → 33 ms、各側 7 回の中央値、後の範囲は 32〜35 ms、1 コアでの JSON パースが上限」です。
- 差を主張するのにリミッタを名指しできないとき、片側がチューニングされないまま走ったとき、問い 4 と 7 を確認できなかったときは、判定を「判断できない」とします。何が欠けているかを名指しします。
- PR 本文の数字は主要な 1 つに絞ります。**Opening a PR** プレイブックに従ってください。実行、範囲、リミッタの証拠は、リンクした成果物かメモファイルに置きます。

## その他の性能の材料

- **Perf issue** プレイブックの baseline は、プレイブックがそれから計画を立てる前に、そしてそのあとのすべての数字も、このチェックリストで検証します。
- **Hillclimb** プレイブックのハーネスは、凍結する前に検証します。凍結したハーネスはエラー数と作業数を出力するので、各 keep-or-revert の判断が問い 4 と 7 をただで確認できます。
