# 検証スキルを作る（Create a verification skill）

まともなプロジェクトには、本物のアプリを操作して振る舞いを証明する、スクリプト化された手段が必要です。起動し、ユーザーと同じやり方で機能を動かし、証拠を残すことです。このスキルはそれを、リポジトリに合わせたプロジェクトローカルのスキル（`.cursor/skills/verify-<app>/`）として生成します。あなたが書くのは、人間向けではなく次のエージェント向けの生成物です。そのエージェントは、アプリを一度も見たことがない状態で、作業の途中に何の前提もなくこれを読みます。

## 1. ユーザーではなくリポジトリに聞く

これらはコードベースから答えます。ユーザーに聞くのは、観察できないことだけです。

- **Surface:** ユーザーが実際に触るのは何ですか？ Web UI、CLI/TUI、デスクトップアプリ、API、モバイルアプリ、ライブラリですか？ リポジトリは複数を持つことがあるので、主要なものを 1 つ選び、残りを記録します。
- **Run:** アプリはローカルでどう起動しますか？ リポジトリ自身が文書化している開発コマンド（package スクリプト、Makefile、README のクイックスタート）を優先します。ポート、環境変数、シードデータ、認証を記録します。
- **Drive:** エージェントはどうやってプログラムから操作できますか？ まず既存のハーネスです。Playwright/Cypress の spec、expect スクリプト、PTY ヘルパー、curl できるエンドポイント、デバッグポートなどです。そのうえで初めて汎用のレシピを選びます。Web と Electron ならブラウザ/CDP、CLI/TUI なら tmux/PTY のハーネス、サービスなら素の HTTP です。
- **Observe:** どんな証拠を残せますか？ スクリーンショット、ターミナルのトランスクリプト、レスポンスボディ、ログ、終了コード、DB の状態です。
- **Isolate:** 2 つのインスタンスを並べて動かせますか（ポート、データディレクトリ、プロファイル）？ 動かせないなら、生成するスキルにそう書きます。共有インスタンスを二重に操作するのを断る方が、ユーザーのセッションを壊すよりましです。

チェックアウトがそのままビルドも起動もしないなら、生成の前にまずそれを直します（または正確に報告します）。壊れた土台に対して書かれたスキルは、間違った手順を教えます。起動を妨げているのが無関係な欠けたアセット（API が決して配信しない静的ディレクトリ、サンプルの設定ファイル）なら、生成するスキルがそれを作ってよいです。検証用の足場だと明確に印を付け、後片付けで削除します。

## 2. スキルを生成する

`.cursor/skills/verify-<app>/SKILL.md` に、YAML フロントマター（`name: verify-<app>` と、アプリ名、ユーザーが触る部分、どういうときに使うかを書いた `description`。フロントマターがなければスキルは決して登録されません）と、次のセクションを書きます。各セクションは、聞き取りで実際にわかったことに根拠を置きます（プレースホルダーを残しません）。

- **Launch:** 検証用にアプリを起動する正確なコマンドと、準備ができたことをどう見分けるか（ログの 1 行、プロンプト）。起動は、空のデータディレクトリから使える状態に到達しなければなりません。マイグレーションとシードデータも含みます。準備完了とは、単にプロセスが応答することではなく、使える状態であることです。データベースのヘルスチェックは通りながら、初期化スクリプトがまだ走っていることがあります。後片付けも含めます。短命な CLI や TUI には生かしておくサーバーがありません。起動とは、バイナリを 1 回ビルド（または依存をインストール）し、その後の各操作をそれぞれ独立した PTY か tmux セッションで始めることです。
- **Doctor:** 「このインスタンスは操作する価値があるか」に答える、読み取り専用のチェックを 1 つ。プロセスが上がっている、バージョン/ビルドが正しい、ポートを自分たちが所有している、認証が有効、を確認します。何かおかしく見えたら、エージェントはまずこれを実行します。
- **Drive:** このリポジトリの実際のセレクタやコマンドを使ったハーネスのレシピ。例ではありません。座標やタブ順より、安定した手がかり（ARIA ラベル、data 属性、プロンプト文字列、ルートパス）を優先します。
- **Evidence:** 証明のために何を残し、どこに置くか。証明の基準を書きます。内部の setter やテスト専用のエンドポイントではなく、本物のユーザー経路を動かします。最後の画面だけでなく、操作とその結果の状態を残します。目に見えるものと同じように、副作用（書き込まれたファイル、挿入された行、送られたメッセージ）も検証します。モックを使うのは、本番の境界がすでに外部システムを隔離している場所だけです。安全な経路が dry-run やテストモードのときは、その名前を信じるのではなく、実際に何を飛ばしているかを観察して検証します（ファイル、ネットワーク、git の ref）。dry-run の中には、今もネットワークに触れたりブラウザを開いたりするものがあります。
- **Cleanup:** 実行が作ったインスタンスをどう片付けるか。プロセス名で kill してはいけません。自分が起動したものを kill します。後片付けが消すのはインスタンスと一時状態で、証拠は消しません。証明の成果物は後片付けを生き延び、スキルが名指しする場所に残ります。
- **Helpers:** スキルが同梱するスクリプトはすべて実行可能で、その呼び出し方がスキル本文に示されています。読者が逆解析しないと使えないヘルパーは、ヘルパーではありません。

## 3. 機能マップの種を蒔く

`.cursor/skills/verify-<app>/features/README.md` と、特定できるユーザー向け機能ごとに 1 ファイルを作ります（まずはルート、コマンド、メニュー、ドキュメントから上位 3〜5 個を目指します）。[`references/feature-map-example/`](references/feature-map-example/) の形に従い、README の索引と機能ごとの 1 ファイルを置きます。各ファイルはユーザーの視点から次に答えます。その機能は何か、どうやってたどり着くか、ハーネスでどう操作するか、動くことを証明する観察可能な最終状態は何か。4 つの H2 は `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、`Gotchas` です。シードデータに、あるジャーニーが必要とする前提条件が欠けているなら、そのジャーニーは失敗を報告し、理由はその機能の `Gotchas` に書きます。通すためにジャーニーを弱めてはいけません。マップはリポジトリが保守する検証の情報源です。マップが別の入口を挙げているのに、都合のよい 1 つの入口だけを動かす証明は不完全です。

## 4. 引き渡す前に生成したスキルを証明する

そのスキル自身の手順を、一度端から端まで実行します。起動し、doctor を走らせ、マップ上の機能を 1 つだけ操作し（1 つで十分です。マップがあるのは、後の実行が残りをカバーできるようにするためです）、証拠を残し、後片付けします。後片付けのあと、証拠が名指しされた場所にまだあることを確認します。証明を食う後片付けは、このステップの失敗です。失敗したものは直し、失敗した反復のあとにも必ず生成した後片付けを実行します。壊れた試行がプロセスやポートを置き去りにしないようにするためです。一度も実行されていない生成スキルは草案であり、成果物ではありません。本物の対象の代役（新しい VM の代わりのコンテナ、リモートの代わりのローカルスタック）で証明したなら、代役がやった準備のうち、対象ではやらないものをすべて挙げます。それらのステップは、本物の対象での実行がカバーするまで未検証のままです。

## 5. 保守のループを提案する

アプリが変わってもマップを正直に保つために、ユーザーに `/maintain-verification-skill` を案内します。頻度を提案するのは、ユーザーが尋ねたときだけです。
