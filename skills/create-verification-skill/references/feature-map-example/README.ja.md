# Notes の検証マップ

このディレクトリは、Notes のユーザー向けの振る舞いを検証するための、保守される情報源です。アプリを動かす前に索引を読み、対応する機能のファイルを手順書として使ってください。

## ベースラインの前提条件

- 使い捨てのデータディレクトリで、`http://127.0.0.1:4173` の Notes を起動してください。
- `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` を設定し、並行する実行が状態を共有しないようにしてください。
- タイトルが `Quarterly plan` と `Grocery list` のノートをシードしてください。
- `control-notes` と `notes` CLI を `PATH` に通してください。
- `control-notes doctor` を実行し、期待する URL、データディレクトリ、ビルドのリビジョンを要求してください。
- この検証の実行が起動していないインスタンスは、決して操作しないでください。

## 操作の規約

- 各手順は、前提条件に別段の記載がない限り、ベースラインの状態から始めてください。
- CSS セレクタや DOM の位置より、ARIA ロールとアクセシブル名を優先してください。
- 各コマンドは文字どおりに扱ってください。引用符付きの名前とフラグは変えないでください。
- ブラウザの操作は `control-notes browser` 経由で行ってください。
- ターミナルの操作は `control-notes cli -- <command>` 経由で行ってください。
- 変更を加えたら、シードしたデータを戻してください。片付けのときに証拠の成果物を消さないでください。

## 証拠とスキップの報告

- 最後の画面だけでなく、ユーザーの操作とその結果の状態を記録してください。
- UI の証拠には、ARIA スナップショットと、アプリの識別子が見えるスクリーンショットを含めます。
- CLI の証拠には、コマンド、stdout、stderr、終了コードを含めます。
- 変更の証拠には、保存された値を読み取り専用の別の画面で見たものを含めます。
- 成果物ごとに、使った機能 ID と入口を記録してください。
- たどり着けない経路は、試したコマンドと満たせなかった前提条件を添えて報告してください。
- 飛ばした入口を、別の経路で検証済みとして報告しないでください。

## 機能ファイルの契約

各機能ファイルは、H1 のタイトルと、ユーザーに見える振る舞いを説明する 1 段落で始まります。そのあと、ちょうど 4 つの H2 の節をこの順で使います。

1. `Sub-features` は短い ID を並べ、振る舞いごとに 1 行を添えます。
2. `How to get to it (user POV)` は、ユーザーの入口をすべて並べます。
3. `Driving it with <harness>` は `Preconditions:` で始まり、各ユーザー操作を正確なコマンドと観察できる結果に対応させた、ラベルの付いた箇条書きを使います。
4. `Gotchas` は、検証の実行を無駄にしたり無効にしたりする罠を並べます。

実装の詳細はマップに入れないでください。ユーザーの経路、安定したハンドル、必要な状態、コマンド、観察できる証拠だけを書きます。

## 機能

- [ノートを作る](create-note.ja.md) は、ブラウザと CLI での作成、キャンセル、永続化、片付けを扱います。
- [ノートを検索する](search.ja.md) は、ツールバー、キーボード、CLI からの検索と、一致、空、クリアの各状態を扱います。
