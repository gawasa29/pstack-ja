# 検証スキルを保守する（Maintain a verification skill）

機能マップは、アプリが変わった瞬間から腐ります。このスキルは、`/create-verification-skill` が生成したスキル（または機能マップを持つ任意のプロジェクトローカル検証スキル）のための保守ループです。厳密さの単位は機能であり、文ごとではありません。すべての機能ファイルをソースから覆い、すべての機能を実際に動かします。ただし箇条書きを 1 つ 1 つターミナルで確かめるわけではありません。

## 結果の分類

1 つを選び、どれだったかを述べます。

- **clean** — すべての機能が、ソースと実際の動作の両方でカバレッジを得ました。出荷する価値のあるものはありません。ブランチも PR も作りません。
- **changed** — 証明済みのドキュメント、ハーネス、マップの修正を 1 本の PR で出荷します。
- **blocked** — カバレッジを終えられなかったか、証明済みの修正を安全に出荷できませんでした。何が止めたのかを正確に述べます。

## 編集してよい範囲

編集するのは検証スキル自身のディレクトリだけです（その SKILL.md、features/、それが持つハーネスのスクリプト）。実行中に製品コードを編集してはいけません。マップが記述している振る舞いをアプリがもうしないなら、それはドキュメントのドリフト（マップを直す）か、製品の退行（報告する。ドキュメントで覆い隠さない）のどちらかです。

## 一巡

0. **対象を見つける。** 保守する検証スキルを探します。本文に launch/drive のセクションと機能マップを持つプロジェクトローカルスキルです（たいてい `.cursor/skills/verify-*/`）。候補が複数あれば、どれかを尋ねます。1 つもなければ、止まって `/create-verification-skill` を案内します。対象をでっち上げてはいけません。

1. **索引の衛生。** 機能マップの README を読み、その兄弟ファイルを glob します。欠けている項目、余分な項目、重複した項目、死んだ項目を直します。軽量に行い、生成された一覧は作りません。

2. **ソースの一巡。** 機能ファイルごとに読み取り専用のサブエージェントを 1 つ、並行して起動します。各サブエージェントは「このユーザー向け機能はどう動くのか」をソースから説明し、ドリフトの可能性を根拠付きで挙げ、実際に動かして確かめる簡潔なレシピを 1 つ返します。子は決してアプリを操作せず、決してファイルを編集しません。返す形は、機能の要約 / ソースの入口 / ドリフトの可能性または無し / レシピ 1 つです。

3. **突き合わせる。** すべての機能ファイルに、返ってきた要約がある状態にします。重なるレシピは、実用的な範囲でできるだけ少ないアプリ状態に統合します。挙げられたドリフトは抜き取りで確認し、問題なしという主張は証明し直しません。最近の変更の多い範囲を一巡し、マップから漏れているユーザー向けの箇所を探します。漏れと判断するには、具体的なソースのパスを要求します。

4. **実際に動かす一巡。** ソースがきれいに見えても必須です。操作はすべてコーディネーターが持ちます。検証スキル自身の起動モデルに従ってください。サーバーと UI なら、長く生きるインスタンスを 1 つ直列に操作します。短命な CLI なら、操作ごとに新しい隔離されたセッションを使います（決めるのはそのスキルの Launch セクションであり、このスキルではありません）。すべての機能を少なくとも 1 回動かし、一巡の間ずっと 3 つの不変条件を守ります。どんな失敗があってもです。(1) 直近で意外な挙動をしてからまだヘルスチェックしていないインスタンスは操作しないこと。最初の操作の前に doctor を走らせ、セッションが単位になる場所では新しいセッションごとに doctor を走らせ、失敗した操作のあとには必ず doctor を走らせます。doctor が失敗を見られない場合（健全なプロセス上の固まった UI 状態）は、望みに賭けるのではなく、既知の状態に戻すか再起動します。(2) それまでに取った証拠が、あらゆる後片付けを生き延びること。名指しされた場所で確認し、想定しません。(3) 操作が始めたものが、その操作の有用性を超えて生き残らないこと。失敗した反復の残骸は、セッションが固まっていても、終了していても、共有されていても片付けます（共有インスタンスなら、インスタンスではなく残骸を片付けます）。スキルのドリフトが原因の doctor の失敗はドリフトです。編集してよい範囲で直し、1 回だけ再試行します。直しが無効にしたものだけを再起動し、それ以上はしません。そのあとで初めて、一巡を `blocked` と呼びます。到達できない機能が `verified-unreachable` になるのは、具体的な前提条件（認証、エンタイトルメント、OS、外部の状態）と、試した経路があるときだけです。マップがその前提条件を書いていないなら、それはドリフトです。トリアージからのハーネスの修正は、出荷する前に実際に動かし直します。最後の後片付けは、その実行の最後の操作のあとに行います。それらの再証明も含みます。何も実行を超えて生き残らないようにするためです（証拠は残ります。スキルに従います）。

5. **トリアージ。** ユーザー視点の説明が間違っているか欠けている → ドキュメントのドリフト。直します。動いている振る舞いをハーネスが操作できない → ハーネスの欠落。直します。ハーネスの修正は、生成時と同じヘルパーのルールに従います（スクリプトは実行可能、呼び出し方はスキル本文に記載）。アプリの振る舞いが実際に壊れている → 製品の欠落。ユーザー向けに記録し、この PR には入れません。

6. **出荷するか止まるか。** changed なら、証明済みの修正を 1 本の PR にし、変更したファイルをすべて先に読み直します。clean か blocked なら、PR は作りません。結果とカバレッジを正直に報告します。

簡潔な実行メモ（覆った機能、到達できなかった前提条件、確認したドリフト、結果）を一時的な場所に置きます。コミットしてはいけません。
