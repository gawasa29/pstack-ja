# コメントをなくす（No comments）

Comment Sicko を立ち上げます。受け入れた所見には対応します。

Comment Sicko の新鮮な視点に従います。

## 範囲

呼び出し元が渡したファイルか diff を使います。無ければ、ベースブランチ（既定は `main`）に対する現在の diff を、ワークツリーを含めて使います。

## 手順

1. `Task` を `subagent_type: "comment-sicko"` で立ち上げます。範囲を渡します。各サブエージェントの推論レベルと fast / standard の速度は、**poteto-mode** スキルの Subagents セクションに従って、その作業に合わせて選びます。そのルールを言い直してはいけません。
2. そのレポートと diff を検査します。アプリケーションコードへの編集、範囲からの逸脱、例外で保護された削除、`MUST KILL` の理由の言い誤り、意図して残したコードを有罪扱いする指摘は却下します。自分たちのコードの意外な点についての指摘は、実行可能なまま残します。そうしたコメントは復元してはいけません。keep が生き残るのは、我々が変えられないものについてだと証明されたときだけです。見落とされたスコープ付きの lint 抑制と TypeScript 抑制を監査します。正しさや安全性に関する抑制は、実行可能な `MUST KILL` のままです。削除の復元は、正確な例外とスコープを絞った証明があるときだけ行います。内容の薄い `IMPORTANT` や `do not remove` の kill / keep を受け入れる前に、そのシンボルに対して `/how` か `/why` を実行します。kill が曖昧なら、復元しません。keep が反証されたか、まだ曖昧なら、削除します。却下したレポートは 1 回だけ取り消して、失敗を名指しして再実行します。2 回目は却下し、未解決として報告し、`/no-comments` を失敗させます。
3. 受け入れた指摘が些細なら、死んだ経路を消す、パラメータを落とす、本物の API を使う、のいずれかで直接直します。修正に形が要るなら、受け入れた集合と周辺コードに対して `/architect` を 1 回実行します。スケッチで止めます。形を作るのは architect です。実装はステップ 4 です。
4. 範囲の中で最小の根本原因の修正を実装します。名指しされた回避策はすべて取り除きます。根本原因が範囲外なら、範囲内で最小の修正を取り込み、残りは未解決として報告します。**principle-fix-root-causes** と **principle-redesign-from-first-principles** のスキルは意図の指針になるだけです。どちらも、囲いを広げることや、囲いの外の事例を直すことを許可しません。症状を塞ぐガードを付け足してはいけません。
5. 制約コメントは `do not remove`、`do not change wording`、`talk to X before changing` のいずれかを言います。我々が変えられないものについての keep は残します。範囲内で最も安い手段、つまり型、実行時チェック、テスト、CI lint で制約を符号化（encode）することを提案します。対話的な承認を待ちます。無人と eval では呼び出し元の事前承認が要ります。承認されたら符号化してから削除します。そうでなければ削除し、制約を未解決として報告し、範囲外の作業をスケッチします。
6. 削除した数、復元したコメント、再実行、architect のスケッチ、修正、符号化の提案、実際の符号化、強制されていない制約、その他の未解決作業を報告します。
