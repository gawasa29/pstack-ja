# プロンプトの言葉遣い

プロンプトが示すのは、意図と完了のチェックです。手順はプレイブックが用意するので、仕様書より平易な数文の方が効きます。

## 入れるもの

- ゴール。何が壊れているか、ユーザーが何を欲しいかを言う。
- 完了のチェック。合否が出せること。「もっと良くして」や所要時間はチェックにならない。
- 見せてほしい証拠。実際のコマンド出力、フローの動画、保存された値、前後の数値を求める。
- ユーザーがすでに知っていること。症状、再現手順、ログ、リンクは、エージェントの検索を省く。
- 本当の制約。「repro first」「don't change any code yet」「zero behavior change」「let me review before proceeding」は、それぞれエージェントの行動を変える。

## 省くもの

- やり方（how）。何を達成するかだけ言い、より良い道を見つける余地を残す。
- スキルや手順の一覧。手書きの順序は、プレイブックが保つ手順を落としたり並べ替えたりする。スキルを名指しするのは、ある選択を上書きしたいときだけ。
- ユーザー自身の原因の推測。エージェントが問題を言い直すまでは。推測を口にすると探索範囲が狭まる。

## まず文脈を積む

- ノイズの多い報告なら、何よりも先に、根本の問題を自分の言葉で、平易な英語で言い直させる。読み違いはコードが生まれる前に見える。
- 新しいチャットでは、その話題の過去の作業を `/recall` する。古いチャットには、新しいエージェントが持っていない文脈がある。
- 慣れないコードを変える前に、仕組みを `/how` に、理由を `/why` に聞く。たどったモデルを持たないエージェントは、最初のありそうな場所で症状を直してしまう。
- ある選択を正当化させたいときは `/teach` に頼む。「原因を直したのであって症状ではないと、納得させて」のように。要約より主張の方が検証しやすい。

## 計画より先に設計

- 最初の設計をそのまま受け取らない。いくつかの案の試作を求め、UI ならスクリーンショットか動画を添えてもらい、証拠から選ぶ。
- 未決の問いは試作に答えさせる。抽象的な計画を敵対的にレビューしない。レビュアーは決して起きないリスクをでっち上げる。
- 共有パッケージや API なら、先に README かチュートリアルを求めてから、コードに戻る。その文書が、エージェントが自分を照らし合わせる目標になる。
- 計画を求めるのは、設計が固まってから。計画の各ステップはチェックで終わる。

## 短く続ける

- チャットがタスクを保持していれば、「do it」「continue」「keep going until done」で十分なプロンプトになる。
- 話題が変わったら「new task」で始める。そうしないと、モードはそのメッセージを次のステップとして扱う。

## 離れる前に

- 「im going to bed」「im stepping away」と言って、エージェントが聞くのをやめるようにする。
- 完了条件は、毎回の反復が実行できるチェックとして書き、その述語を `/loop` に渡す。
- 名前を付けたベースから新しいワークツリーを切るよう頼む。
- エージェントが止まりかねない点にあらかじめ答える。「don't ask me before committing」のように。
- 後で監査する決定ログを求める。
- 出口を用意する。「if you're truly stuck after a few hours, stop and write up why」。

## 1 行で軌道修正

- ゴールを言い直す。「i said the goal is to repro. i did not ask for a fix yet.」
- 原則を名指しする。「apply prove it works. show me the real output, not the build log.」
- 原則の名前が効くのは、エージェントがすでにそのルールを読んでいるから。返答は、そのルールが変えた判断を名指しする。
