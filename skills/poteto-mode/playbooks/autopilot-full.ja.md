### 自動操縦フル（Autopilot-full）

**判定はあなたが持ちます。PR は決して持ちません。各 PR は1人のオーナーがビルドからマージまで運び、コードを書いていないあなたの swarm が、取り込まれるコードを証明するまで何もマージされません。**

判定は1つのパッチを覆い、グリーンの CI は1つの head を覆います。ステップ 4 のフルの swarm は1回だけ走らせ、もう一度走らせるのは大きな変更のときだけです。`playbooks/shipping.md` の patch-id のルールはレーンの結果を引き継げますが、新しい head にはそれぞれグリーンの CI が要ります。

1. **オペレーターのゲートが最優先です。** 委任が覆うのはキューの項目だけなので、オペレーターが自分の担当だと名指しした項目と、キュー外の PR は merge-ready で止まります。計画を述べろという依頼は、実行の許可ではありません。
2. **PR ごとにオーナーを1体起動し、その作業を後任が見つけられる場所に残します。** forge はプログラムで一度だけ確定します。既定は GitHub CLI（`gh`）です。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、PR の操作はすべて `origin pr` を使います。そうでなければ `gh` のままとし、フォールバックを記録します。Graphite（`gt`）を必須にしてはいけません。各オーナーは Cursor のクラウドエージェントで、ビルドし、`playbooks/opening-a-pr.md` に従って PR を開き、本物のアーティファクトで変更を証明し、`playbooks/babysit.md` に従ってグリーンまで見守り、ステップ 4 と 5 を通ったらマージします。

   PR は早めに開き、CI とボットが作業と並行して走るようにします。コードが完成と言えるのは、slop の削ぎ落とし（`cursor-team-kit` プラグインの `deslop` スキル（`/deslop`））と `/no-comments` のパスを終えた後です。フルの swarm は仕上がったコードで走らせます。そのうえで現在の trunk へリベースし、自己証明の前に code-ready の head を報告します。検証が、パッチが取り込まれる base の上で走るようにするためです。その後の head はすべて報告し、自己証明、CI、見守りが済んだら merge-ready を報告します。修正のラウンドは、trunk がコンフリクトする、CI を壊す、同じファイルへの既知の並行変更を取り込む、のいずれかが無い限り、その base の上で続けます。リベースのたびに CI がやり直しになるからです。リポジトリのチェックは、触ったパスについて、コミット済みの head で、code-ready の push の前と、検証エージェントが要る後続の push の前に実行します。

   VM は死ぬものとして進めます。始めてすぐに push し、**show-me-your-work** スキルに従って、ルートエージェントのストア（パスはシステムプロンプトにあります）に決定の記録を付け始めます。以降は、1つの単位を仕上げるたびに、次を始める前に push します。サブエージェントを起動した者は、その id、状態、同種の過去実行から見た「これ以上かかったら詰まり」の時間をそのストアに記録します。親が死んでも、ルートがそれを調べられるようにするためです。force-push してよいのは自分のブランチだけで、`--force-with-lease` を最後に push したか引き継いだ SHA に固定します。自分がしていない push があれば、止まってルートに報告します。
3. **オーナーは trunk から並行に走らせ、決してスタックしません。** 各 PR が単独で取り込まれるようにするためです。
4. **swarm での検証は1回。** フルの swarm は code-ready の head で1回だけ走らせます。もう一度フルで走らせるのは、新しい振る舞い、作り直し、大きな新しい diff のときだけです。リベース、マージコンフリクトの解消、軽微な修正は新しい head での検証エージェント1体で済ませ、文言だけの変更は無しとします。**swarm** スキルに従い、code-ready の SHA で独立した検証エージェントをファンアウトします。彼らはゲートを再実行し、要となる振る舞いを、制御スキル（`cursor-team-kit` の `control-ui` や `control-cli` など）か名指ししたドライバーを通して本物のサーフェス上でライブで証明し、diff を監査します。ライブのレーンが無ければ判定はクリーンになりませんし、merge-ready の報告の証跡をあなたが監査する前もクリーンになりません。どのレーンも、自分が確かめていない主張は信じないからです。

   PR をブロックしてよいのは、示せる問題があるときだけです。head での失敗した実行か、その PR が誤らせたドキュメントの行です。PR の base がすでに持っている問題は、trunk であれスタックの下の PR であれ、その PR がその問題のコードをコピーしたか、新たにその問題へ到達したのでない限りブロックしません。ブロックするのは、ユーザーが踏むバグ、落ちたゲート、出荷済みドキュメントの誤りだけです。それ以外はフォローアップに回します。
5. **オーナーがマージするのは、あなたが検証し、取り込み先の trunk で試したものだけです。** グリーンの CI だけではマージを許可しません。swarm のレーンが動き出したら、マージ準備として現在の trunk へリベースし、新しい head を報告して、グリーンの CI を待ちます。

   マージの直前に trunk を fetch し、その変更がパッチに影響しうるかを問います。trunk が動くたびにリベースしていては終わらないからです。取り込まれるコードが未検証になる場合は、リベースして CI を待ちます。コンフリクト、両側が変更したファイル、PR で走るチェック自体の変更などです。両側が変更した lockfile は、凍結インストールがマージ結果で通り、PR が変えるパッケージがそこで head と同じように解決するなら、リベース不要です。そのインストールは取り込まれる lockfile を試すものだからです。インストールが落ちるなら、リベースで直さなければなりません。trunk がパッチの呼び出し元や、パッチが依存するもの（呼ぶコード、依存のバージョンなど）を変えたときは、マージ結果でパッチのチェックを回し、通ったらマージします。それ以外はマージします。マージ準備の後に trunk が3度目のリベースを強いるなら、いったん止めてルートに報告します。ルートが衝突する作業の順序を決めます。
6. **ルート層を回します。** ゲートを緩めるものはすべて、予算の引き上げや allowlist への追加であっても、検証エージェントの証明と、そのうえでのあなたの新しい副署が要ります。グリーンにしたいのはオーナー自身だからです。承認まで覆う委任の下では、その副署が承認になります。オーナーが残すその記録は、レーンが確認できるようにあなたの副署を指します。無効化されたチェックや、失敗しても止めない（ソフトフェイル）チェックは、必ず外します。すべてのケースを守らなくなるからです。forge が強制する承認を与えたり迂回したりすることは決してしません。副署ではそれを覆えないからです。

   オペレーターの許可が出たら `/loop 1h` を仕込み、委任した作業が無くなるまで監査します。長い実行はドリフトし、エージェントは黙って止まるからです。各 tick はこのプレイブックを trunk から読み直し、報告されていない head や記録されていないエージェントといったドリフトを、オーナーに記録させて直します。ドリフトは記録の欠けであって、停止ではないからです。末端のレーンまで全エージェントを調べ、それぞれを副作用で判断します。状態のテキストや要約は、詰まった子を隠しうるからです。エラーになる、ターンを開始できない、stuck-after の時間を過ぎても新しいものが出ない、のいずれかなら詰まっています。最初の tick までに push も記録の行も書いていないオーナーも同じです。あなたやオペレーターの返答を待っているものは詰まっていないので、答えます。詰まったエージェントは、停止が届くのを待たずに即座に差し替えます。オペレーター向けに何かを変えた tick は、**ketchup** スキルに従って状況を伝えて終わり、何も変えなかった tick は静かに終わります。
7. **オペレーターの停止指示には即座に従います。** 保留は、書き込みゼロの命令として全オーナーに届きます。各オーナーは自分の状況を報告し、オペレーターが解除するまで自分の任務を保ちます。

**返信内容：** **ketchup** スキルに従ってオペレーターに状況を伝えます。各 PR の状態と判定、マージされたもの、副署とその理由、オペレーターのゲートで開いているもの、保留にしたフォローアップを、各 PR と記録へのリンク付きで示します。
