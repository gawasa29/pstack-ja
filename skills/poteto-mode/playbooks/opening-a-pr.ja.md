### PR を開く（Opening a PR）

他のすべてのプレイブックの最後に呼ばれます。

**ワークツリー。** main から切った git ワークツリーで作業します。サブエージェントはそれを引き継ぎます。同じブランチに対する複数の `Task` 呼び出しは、それぞれ自分のワークツリーを持たせるか、呼び出しの間に `git fetch && git reset --hard origin/<branch>` を挟みます。無関係な作業が載った汚れたブランチなら、パッチとして外に出し、新しいワークツリーで当てます。絡まったワークツリーは、main からリセットし、最小限でやり直します。

**コミット。** コミットは惜しまずに行います。PR を開く前に、小さく順序立ったコミットにリベースします。各コミットは将来の PR です。取り込める単位で、筋道が分かる順に並べます。直しが直前に作ったコミットに入るべきなら amend し、分けられるなら新しいコミットにします。コミット本文で主題を言い直しません。

**PR。** コミットの前に `cursor-team-kit` の `/deslop` を diff に掛け、レビューの前に `/no-comments` を実行します。PR のタイトル、説明、コミット本文はすべて `/technical-writing` で書き（Diátaxis 以外のすべての層、かつ STE の語彙ルールを適用します。動作ごとに1語、冠詞は残す、`-ing` より素の動詞が使えるならそちら）、そのうえで `/unslop` を適用します。

**タイトル。** Conventional Commits の `type(scope): subject` とし、末尾にピリオドを付けません。type は `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`perf` などです。scope は領域で、`pstack` や `poteto-mode` などです。subject は短い命令形で、変更を担う実在のシンボルがあればそれを名指しします。例は `fix(pstack): retarget opening-a-pr babysit trigger` です。

**説明。** PR 本文は、diff を持っているレビュアーへの1分のブリーフィングであり、実験ノートではありません。その変更がなぜ存在するのか、何を入れないのか、何を壊しうるのか、どう動くと証明したのかを書きます。短く単純な文で、識別子は少なめにし、文章の壁を作りません。本文は squash コミットの本文になるので、そのコミットは40行程度に収めます。`##` の見出しを使い、太字の小見出しは使わず、次の順に並べます。言うことが無い節は落とします：

- `## Why`：問題とアプローチを1〜3文で。SHA、リベースの系譜、「main を基にしています」という前置きは書きません。
- `## What changed`：短い箇条書きを1〜3個。実際のシンボルやパスは、それが変更を担うときだけ名指しします。リネームや向き先変更では両側の名前を書きます。
- `## Scope`：必ず書きます。何を覆い、何を意図的に外したか（フォローアップ、既知の欠け）を短く1〜3項目。シンボル、パス、ファイルごとの評論は書きません。
- `## Tradeoffs`：レビュアーが聞いてきそうな、却下した代替案だけ。本当に選択が無かったなら省きます。
- `## Blast Radius`：誰に何に触れ、なぜそれが安全か危険かを1〜2文で。main が赤いなら、赤いままにするコストを述べます。
- `## Verification`：箇条書きを1〜3個、それぞれ実際に走らせた経路とその結果。性能なら、単位付きの主要な数値を1つ、`before → after` で示し、残りは arena か swarm のディレクトリへのリンクにします。サンプルサイズの方法論、swarm の朗読、指標の表は書きません。

節の後ろに、主張を証明する動画やスクリーンショットを添えます。完全な SHA、swarm や arena のレーンの朗読、レバー修正の随筆、ファイルごとのチェックリスト、`CLEAN` の判定は、本文ではなくリンクしたアーティファクトに置きます。

**forge。** 最初の PR 操作の前に forge を確定し、create、edit、view、watch、merge でその選択を保ちます。既定は GitHub CLI（`gh`）です。`command -v origin` が成功し、Origin がリポジトリを解決できるなら `origin pr ...` を優先します。Origin が無いかリポジトリを解決できないなら `gh` のままとし、フォールバックを記録します。Graphite（`gt`）を必須にしてはいけません。

**組み込みの PR ツール。** 実行環境が組み込みの PR ツールを提供しているなら、作成、編集、向き先変更、ready への変更はそれを通して行い、forge の CLI では決して行いません。CLI で作った PR は、そのツールが追跡しているものを取りこぼします。ツールが覆わないすべてのこと、およびそうしたツールが無い実行では、確定した forge を使います。

**サイズとスタック。** 大きな PR 1本より、細い PR 5本を選びます。スタックとは base ブランチの連鎖です。根の PR は trunk を向きます。各子ブランチは親の先端そのものへリベースし、その PR は親ブランチを向きます。親がマージされたら、`playbooks/shipping.md` のステップ 4 に従って子を trunk へ移します。組み込みの PR ツールが無い場合は、確定した forge に従い、子は `origin pr create --status open --base <parent-branch>` か `gh pr create --base <parent-branch>` で作り、向き先の変更は `origin pr edit <pr> --base <parent-branch>` か `gh pr edit <pr> --base <parent-branch>` で行います。trunk から切るのは独立した作業のときだけです。まとまったスタック作業の前には trunk でリベースします。

**ready 状態。** PR はすべて ready で開き、draft にはしません。組み込みの PR ツールは draft を既定にすることがあるので、それ経由の作成呼び出しすべてで `draft: false` を設定します。Origin なら `--status open` を渡します。`gh` なら `--draft` を付けません。それでも draft で開いてしまったら、PR ツール経由で ready にするか、確定した forge に従って `origin pr ready <number>` か `gh pr ready <number>` を実行します。PR の状態に言及する前に `origin pr view <number>` か `gh pr view <number>` を実行します。

**見守り。** PR を開いても見守りは始まりません。URL を投稿して、ビルドを続けます。まずフェーズかスタックを仕上げてください。別途の見守りのパスを回すのは、スタック全体ができた後にユーザーが頼んだときだけです。新しい PR ごとに見守ると、ビルドが滞り、あとの波でやり直しになるコミットにチェックを使います。フィードバックが意図からずれているなら押し返してください。

PR を開いたサブエージェントは `/deslop` と `/no-comments` を実行し、URL を投稿します。Autopilot-full か Autopilot-stack のオーナーでない限り、見守りはせず親に戻ります。そのオーナーの任務には見守りのループが割り当てられており、それが `playbooks/babysit.md` の待つ依頼です。オーナーは code-ready の報告の後にループを始め、merge-ready を報告します。また、スタック全体ができるまで見守りを待つ、ここおよび `playbooks/babysit.md` のルールからは外れます。
