### 編成（Orchestrate）

**あなたが回すのはプログラムであり、コードではありません。どの作業をどのエージェントがやるかを決め、それぞれが出すものを確認します。** 1つのコーディネーターチャットに預ける常設プロジェクト向けで、数日にわたり、多数のスタック PR、数十から数百のサブエージェント、人間の出番はわずかです。1つのタスクを述語まで駆動するのが Autonomous run です。専用のワークフローが必要な意欲的な実行1回は figure-it-out です。1体のエージェントがセッションの予算内で終えられる作業は、プログラムではありません。

自分の道具で回します。ワーカーは `Task` で起動します。プログラムの状態は Project のトラッカー（`notes.md`）と Project ストアに置きます。ハーネスに PR と CI のイベント購読があるなら、それで各 PR を見張ります。スクリプトを呼ばず、ポーリングループも回さず、エージェント間でメッセージや状態を中継することも決してしません。

#### トポロジー

- **PR ごとに1オーナー。** オーナーはそのブランチの唯一の書き手であり、ビルドからマージまで PR を運びます。push、リベース、向き先の変更もオーナーだけが行います。base の PR を閉じたり向き先を変えたりすると、その上の PR がすべて孤立するので、オーナーはあなたの指示があるときだけそれを行います。あなたはコードを書くことも編集することもしません。コンフリクトしたマージ、連鎖のリベース、修正はオーナーに渡します。
- **独立したタスクごとに新しいワーカー。** そのキックオフには必要なものをすべて載せ、依存する上流の報告も1つ残らず全文貼り付けます。ワーカー同士は互いが見えません。このマシンが必要な場合を除き、ワーカーは新しいクラウド VM（`environment: "cloud"`）で動かします。`control-ui` や `control-cli` の実行時チェック（`cursor-team-kit` のもの）、ローカルのトランスクリプト、シミュレータ、ここにしかない認証が要る場合です。サブエージェントごとに、その作業に合った推論レベルと、fast か standard の速度を選んでください（Subagents セクション参照）。
- **サブコーディネーターを置くのは、1つの領域に並行ワーカーが多いときだけ。** その領域のワーカーとキックオフを所有し、あなたには1つのまとめだけを送り、生のワーカー報告は送りません。階層は3段で止めます。あなた、サブコーディネーター、ワーカーです。コーディネーターあたり10体ほどのワーカーを同時に動かし、まとめて待つのではなく、1体終わるごとに次を始めます。
- **新しい作業がワーカーの築いた状態を必要とするときはフォークします。** チェックアウト、未コミットの変更、動いているプロセスなどです。ワーカーへのメッセージは、同じ作業のフォローアップのときだけにします。様子を見るためにメッセージを送ってはいけません。メッセージは待機中のエージェントを再起動させます。
- **各 PR には、作者ではない検証エージェントを付けます。** 別のモデルファミリーのものです。オーナーがマージするのは、その検証エージェントが現在の head で合格を出したときだけです。
- **1つの単位から始めます。** ファンアウトする前に、キックオフ、オーナー、検証、マージまで通します。キックオフの欠陥が50体ではなく1体分の損で済みます。ほぼ同じで安い単位なら、最初の1単位がその試験です。

#### 監督

- **各キックオフには、作業が終わったことを示す証拠を書きます。** コマンドと期待する出力、制御スキルによる確認、アーティファクトなどです。あわせてゴール、ワーカーが書いてよいパスと書いてはいけないパス、取ってはいけない行動も明示します。証拠を名指しできないなら、その単位はまだ範囲が定まっていません。
- **ワーカーの要約だけでなく、diff かアーティファクトを読みます。** グリーンの CI は判定への入力であって、判定ではありません。振る舞いの作業には型チェック以上のものが必要です。判定は1つの head SHA に対するものなので、新しい push には新しい判定が要ります。各サブコーディネーターのキックオフを、そのワーカーが動いている間に抜き取りで読み、失敗があれば指示を直します。
- **範囲からずれた作業や、頼まれた以上に膨らんだ作業は差し戻します。** 残すのはプログラムを妨げる修正だけにし、他はフォローアップとして保留します。
- **PR について報告する前に、そのライブの状態を確かめます。** `gh pr view` と `gh pr checks`、または使っている forge の同等品で確認し、ワーカーの最後の報告には頼りません。起動したワーカーはすべて、完了、差し替え、他のワーカーの範囲への吸収、のいずれかとして説明します。
- **止まったワーカー、ループするワーカーは停止させるか差し替えます。** 判断材料は push と PR の動きであり、状態のテキストではありません。原因別に再試行します。コンテキストやメモリの上限なら範囲を小さくし、接続断なら同じキックオフ、ツールのエラーなら別のモデルです。2回再試行してもだめなら、その単位を落として周りを組み直します。止めたワーカーが遅れて戻ってきたら、結果を PR の現在の状態と突き合わせ、固有の発見は新しいワーカーに渡します。
- **ユーザーに聞くのは、本当の判断かブロッカーだけです。** 不可逆な操作、実験では決着できないプロダクト判断や好みの判断、組み直しを経ても残った行き止まりなどです。リベースの手順、再試行、CI のフレーク、レビューの仕分け、「続けていいか」はユーザーに届きません。

**返信内容：** ゴールに対して何が取り込まれたか、各 PR のライブの状態と判定（リンク付き）、落としたものとその理由、ユーザーの判断待ちの項目。
