### 出荷（Shipping）

**何が取り込まれるかはあなたが持ちます。各 PR を独立に検証し、検証済みの連続区間だけを根から取り込み、その後はスタックに触らないでください。**

1. **forge を確定し、そのうえで各 PR を取り込む前に独立に検証します。** 既定は GitHub CLI（`gh`）です。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、PR の操作はすべて `origin pr` を使います。そうでなければ `gh` のままとし、フォールバックしたことを記録します。Graphite（`gt`）を必須にしてはいけません。PR ごとに検証エージェントを1体ずつ置きます。いずれも Cursor のクラウドエージェントで、ユーザーと同じやり方で変更を動かします。対応する制御スキル（`cursor-team-kit` の `control-ui` や `control-cli` など）を使い、親と head を突き合わせ、その PR に `PASS`、`PASS+NOTES`、`FAIL` のいずれかを投稿します。数えられるのは、コードを書いていないエージェントの判定だけです。作者は自分が作ろうとしたものを確認するからです。グリーンの CI とボットの承認レビューは判定ではありません。どちらも、ユーザーと同じやり方で変更を動かしてはいないからです。
2. **取り込むのは、一番下を根とする、検証済みの連続した区間だけです。** 未マージの最も下の PR から上へたどり、`PASS` か `PASS+NOTES` の無い最初の PR で止まります。その下の PR が区間で、一番上が天井です。未検証の PR の上にある検証済みの PR は待ちます。下のコードが無ければ取り込めないからです。そのコードをブランチに持たず、必要ともしない PR は、trunk に移して単独で取り込めます。ただし先に新しい判定が要ります。古い判定はそのコードを下に敷いて走っており、trunk にはそれが無いからです。
3. **判定が今もそのコードを指しているか再確認します。** 判定はパッチに対するもので、連鎖のリベースは、どのチェックも落とさずに上のすべての PR を新しい SHA へ動かします。古い判定を信じる前に、判定時の SHA と現在の head で `git patch-id` を比べます。パッチの違いがテスト、ドキュメント、lint 設定だけなら、走らせたものが両方の SHA でノイズを除いて同じにビルドされる場合に限り、そのレーンの結果は有効です。ノイズとは、判定時の SHA を2回ビルドした間にも現れる差分、または埋め込まれたコミット SHA のことです。ノイズの種類ごとにファイルを添えて報告し、読む人が判断を検算できるようにします。変更そのものには新しいチェックとレビューが要ります。古い判定はその変更を見ていないからです。開発サーバーのようにビルド出力の無いレーンではこれを示せないので、再実行し、他に動いたものも再検証します。
4. **下から上へ、1本ずつ取り込みます。** 常に区間で最も下の未マージ PR を、`origin pr merge <pr>` か `gh pr merge <pr> --squash` でマージします。Origin では素のコマンドが、指定した PR より下のすべての PR もマージします。GitHub では、base がまだ親のブランチである PR は、trunk ではなくそのブランチにマージされます。結果は PR を読み返して確認します（`origin pr view <pr>` か `gh pr view <pr> --json state,mergedAt,baseRefName`）。マージキューが PR を並べただけでもマージコマンドは成功を報告しうるし、依頼した自動マージはマージではありません。取り込まれた PR は、base が親のブランチではなく trunk になって merged と読めます。`--auto`（Origin の merge-when-ready、GitHub の auto-merge）を仕込むのは、判定が現在の head を覆っている PR だけです。どの head が準備できていても、それが取り込まれてしまうからです。マージが取り込まれたら、base がマージされたブランチだった PR の向き先を trunk に変え（`origin pr edit <pr> --base <trunk>` か `gh pr edit <pr> --base <trunk>`）、そのパッチをマージ結果の上へ移し、`--force-with-lease` で push します。判定はパッチを覆うものでコミットを覆うものではないので、判定が残るかはステップ 3 の patch-id のルールが決めます。チェックが通り、判定が残ったらマージします。
5. **取り込みが進む間はスタックに触りません。** ブランチや base に加えてよい変更は、ステップ 4 の次の PR の移動だけです。マージは、その瞬間にブランチと base が持っているものを、判定の有無にかかわらず取り込むからです。GitHub では、`playbooks/babysit.md` のキューの監視役（`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`）を `/loop` の下で回し、天井で `COMPLETE` を報告するまで見ます。Origin では、`origin pr checks <pr> --watch` が返るたびに `origin pr view <pr> --checks` で現在の PR を読み直し、天井が merged になるまで続けます。親がマージされたときに base が trunk へ移るのは想定内で、直すべき損傷ではありません。マージが止まったら、何かを変える前に理由を突き止めます。
6. **天井で止まります。** 区間を延ばすには新しい判定が要るので、ステップ 1 からやり直す新しいパスになります。

**返信内容：** 検証済みの区間とその天井、各 PR の判定と出した主体、取り込まれたものとその確認方法、次の欠けを埋めるのに必要なもの。
