### トレースフォレンジック（Trace forensics）

**アーティファクトからの診断はあなたが持ちます。**

動いているプロセスに計測を仕込む **Runtime forensics** とは別です。ここではキャプチャがすでにあり、アーティファクトは固定されたデータセットなので、再実行せず読みます。道具は汎用のものに限ります。cpuprofile と `.json.gz` には DevTools かトレースパーサー、spindump にはテキストエディタ、heapsnapshot には手持ちのヒープ解析ツールです。

1. 形式を見極め、適切な道具で読み込みます。大きなアーティファクトの解析はサブエージェントで行い（**principle-guard-the-context-window** スキル）、絞り込んだ所見だけをメインスレッドに残します。サブエージェントごとに、その作業に合った推論レベルと、fast か standard の速度を選んでください（Subagents セクション参照）。
2. 生のアーティファクトを、問い合わせできる形に変換します。トレースやヒープスナップショットを sqlite に落とし、サンプル、フレーム、ノードごとに1行にします。読む前に問い合わせ可能な形まで持っていきます。
3. 原因まで絞ります。最も時間を占めるフレームを問い合わせ、コールツリーをたどってホットパスに至ります。リークなら、リークしたオブジェクトから GC ルートまでの保持チェーンを追います。spindump なら、CPU 上で張り付いているかブロックしているスレッドと、その待機理由を探します。
4. ソースに紐づけます。ホットなフレームを、アーティファクト自身のシンボル情報を使ってファイル、シンボル、行に対応づけます。ソース対応の無いフレームは、まだ診断ではありません。シンボルを解決するか、アーティファクトがそれを持っていないと明言します。
5. 対になるキャプチャがあれば、前後のアーティファクトを diff して確認します。無い場合は、その所見を、アーティファクトが支える最強の仮説として示し、確定した原因とはしません。
6. 引用付きの診断を返します。頼まれない限り修正はしません。原因が分かったら Bug fix か Perf issue に振ります。スループットのチェックポイントは1行のままです。`throughput checkpoint: n/a, read-only forensics`。

**返信内容：** アーティファクトとその形式、絞り込んだ所見、ソースの位置、アーティファクトのパス、対になるキャプチャで確認できたかどうか。
