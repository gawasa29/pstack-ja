# Test Behavior, Not Implementation

テストは、コードがその利用者（呼び出し側、エンドユーザー、あるいは別のサービス）に対して何をするかという主張です。振る舞いとは、それらの利用者が自分たちが使うインターフェースを通して観察できるものです。戻り値、エラー、読み戻せる状態、そしてコードの外のシステムへの効果を含みます。リクエストが送られた、行が書かれた、メッセージが出た、といったものです。実装とは、利用者が観察できないものです。private なヘルパー、内部の呼び出し順、中間データ、どの内部の協働者が仕事をしたかです。

それぞれのテストを、2 つの想定された編集に対して判定します。

- **振る舞いを壊す。** コードが誤った値を返す、効果を飛ばす、効果を 2 回行うようにします。それでもテストが通るなら、そのテストは何も証明していません。よくある原因は、契約より緩い assert、テスト対象のコードが計算した期待値、値を読むコードを一度も実行しないまま定数やプロンプト文字列を書き写した期待値、テスト自身が組み立てたデータへの assert です。
- **内部を変える。** 観察できる結果をすべて同じに保ち、下のコードを組み替えます。それでテストが落ちるなら、そのテストは実装に固定されています。リファクタのたびに書き直しが要り、それでもバグは捕まえません。

1 つ目の編集を捕まえ、2 つ目を生き延びるテストを残します。残りは書き直すか削除します。両方を満たすテストを書くには、具体的な入力で、利用者のインターフェースを通してコードを動かします。期待値は要件から導き、コードの実行から導きません。契約が約束することを、それより少なくも多くもなく assert します。

決めるのは契約であり、assert の形ではありません。「空のカートは決して課金しない」が約束なら、決済クライアントが呼ばれなかったという assert は振る舞いです。課金が起きるケースと対にして、テストが呼び出しを見られることを示します。モックした外部サービスが受け取るペイロードは振る舞いです。そのサービスがそれを観察するからです。内部ヘルパーへの呼び出しは実装です。どの利用者にも見えないからです。一致するレコードがないときの空リストは正確な答えですが、テストが何らかの結果を必要としているだけなら、空リストの assert は中身のないチェックです。正確なエラーメッセージは、どの呼び出し側も読まない文言を固定します。呼び出し側が分岐に使うエラーの型は契約です。

テストは呼び出しではなく不変条件を固定できます。2 つのテーブルに存在しなければならないキーや、コンパイル時の型チェックなどです。不変条件は振る舞いです。
