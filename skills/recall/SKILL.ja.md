# 文脈を思い出す（Recall）

**作業を始める前、または再開する前に、ユーザーの直近の作業コンテキストを組み立て直し、今どこにいて次に何をするのかを凝縮したカプセルとして返します。**

簡潔に、話題から外れずに保ちます。対象範囲のスレッドが必要とするものだけを読み、そこで止めます。

あなたのコンテキストは 2 つの記録にあります。自分自身のチャット履歴には、あなたが行ったことと決めたことが残っています。共有の記録には、同じコードの周りで別の名前の下に起きたことすべてが残っています。ユーザーが繰り返し報告する症状、出荷されてから取り消された修正、本番で今も出ているエラーです。2 つ目の記録を検索するのが **why** スキルで、ソース管理、課題トラッカー、チャットと課題のチャンネル、長文ドキュメント、エラートラッキングを横断します。バグを長く引きずる機能は、その話の大半をそこに置いています。だからトランスクリプトだけで組み立て直してはいけません。

トランスクリプトは `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl` にあります。`<slug>` はワークスペースのパスから先頭のスラッシュを落とし、各 "/" を "-" に変えたものです（`/Users/you/proj` は `Users-you-proj` になります）。各行が 1 つのチャットメッセージです。

1. 分類してから振り分けます。再開したい特定の過去チャット 1 つは `session-pickup` プレイブックの担当で、これではありません。習慣を長く使えるスキルにするのは `automate-me` です。自分の作業を人間が読める形で要約するのは別のタスクです。recall は行動する前に、直近の複数のチャットから作業コンテキストを読み込みます。ユーザーがすでに状態のカプセル（パス、ブランチ、変更内容）を丸ごと渡してくれているなら、それを使い、掘り起こしは省きます。
2. 検索する前に範囲を固定します。期間（"recent" は現実の範囲で、既定は直近 7 日）、指定があれば話題、ワークスペース（既定は現在アクティブなもの。頼まれていないのに他のプロジェクトのトランスクリプトを読んではいけません）を決めます。範囲を言い返します。"all" を黙って "recent N" に変えてはいけません。
3. チャット履歴に横断的に広げます。並列のサブエージェントを速く安いモデルで立ち上げ、それぞれがコーパスの一部を担当します。すべてのサブエージェントに次を伝えます。候補は実際の更新時刻（`ls -t`）で並べ、UUID 名では並べないこと。まず話題を grep し、それから一致したチャットだけを、しかもその中の関係する範囲だけを読むこと。現在のチャットと明らかなノイズ（サブエージェント、eval、テストのチャット）は飛ばすこと。各サブエージェントは同じスキーマで、チャットごとに 1 ブロック返します。話題、ユーザーの目的、決定、未解決のスレッド、苦戦と訂正、成果物（PR、チケット、ブランチ）で、それぞれチャットの UUID を引用します。チャットが 1〜2 個なら、ファンアウトを省いて直接検索します。生のトランスクリプトはサブエージェントの中に留めます。メインスレッドが受け取るのは所見だけです。各サブエージェントの推論レベルと fast / standard の速度は、**poteto-mode** スキルの Subagents セクションに従って、その作業に合わせて選びます。
4. 話題が機能、ファイル、サブシステム、領域、バグのいずれかを名指しするときは、必ず共有の記録も一掃します。これは判断ではなく既定で、"my work on X" でも免除されません。**why** スキルのソース調査役に渡しますが、問いは「なぜこう作ったのか」から「今の状態はどうか、何が試されて定着しなかったか、ユーザーは今も何を報告しているか」に振り向けます。そのソース別プレイブックを再利用し、調査役をチャット履歴の掘り起こしと並行して走らせ、構えも引き継ぎます。1 ソースにつき調査役 1 人、空の結果も所見として扱う、使えない MCP は飛ばしてそう告げる、という構えです。返ってきたものはブリーフに畳み込みます。このステップを省くのは、名指しの対象が無い純粋な活動の想起（"what did I do this week"）だけです。その場合は自分の履歴とライブ状態が答えのすべてです。
5. ライブ状態と突き合わせて検証します。掘り起こしと一掃で浮かんだ PR、ブランチ、チケットを取り出し、`git` と `gh` で確認します。答えがエージェントが実際にやったこと（実行したツール、読んだファイル、踏んだエラー）に懸かっているときは、切り詰めたローカルコピーではなく、トランスクリプト全体を読みます。
6. ブリーフを下の契約に沿って書きます。スレッドごとにまとめ、名指しされた話題から外れません。

## 出力の契約

カプセル、スレッドの状態、問題、次の一手の順で書きます。より詳しい内容は下に回すか、削ります。

- **カプセル。** 最大 5 項目。この作業が何で、全体としてどこまで進んでいるか。
- **スレッド。** 1 行ずつ、ちょうど 1 つの状態タグを前に付けます。`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]`、`[planned, not started]` のいずれかです。タグの無いスレッドはまだ完了していません。タグを付けてください。
- **問題。** 最大 5 つ、繰り返し起きているものです。ユーザーが繰り返し報告する症状と、出荷されて取り消された修正を含めます。次の試みが、前回失敗したところから始められるように。
- **次の一手。** 最も有用な次の行動を 1 つ、具体的に。

隣接する機能やチケットは、これの妨げにならない限り外に置きます。カプセルとスレッドの行が画面からはみ出すときは、スレッドを削る前に詳細を削ります。ブリーフは **unslop** スキルを通して書き、チャットの所見は UUID で、共有記録の所見はその出所（PR #、チケット ID、チャットのパーマリンク、エラートラッカーの issue）で引用し、公開出力の前には私的な文脈を除きます。

**返答:** 上の契約に沿ったブリーフ。
