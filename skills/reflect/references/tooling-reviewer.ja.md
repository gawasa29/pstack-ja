## レンズの追加: エージェントの自己充足

ユーザーが手で渡した文脈を、エージェントが MCP ツール（チケットトラッカー、チャット、ドキュメント、オブザーバビリティ、エラートラッカー、ソース管理、分析用のウェアハウス、CI、デザインツールなど）や別のスキルで自分から取りに行けた場面を、すべて挙げてください。各項目について:
- 原則: エージェントが自動で調べるべきだったことを 1 文で。
- 証拠: ユーザーが手で渡したもの（チケット ID、チャットスレッドの URL、オブザーバビリティのトレース ID、エラートラッカーのイベントリンク、「これは PR #X から」、デザインツールの URL など）。
- ルーティング: この場面のワークフローを所有するスキル。次回のエージェントが自分で文脈を取りに行けるよう、そのスキルが該当する MCP ツールや兄弟スキルを呼ぶように拡張します。

このパターンの例:
- エージェントがチケットトラッカーの MCP を問い合わせなかったため、ユーザーがチケットのタイトルを貼り付ける。ルーティング: 該当するトリアージのスキルが、まずチケットトラッカーの MCP を呼ぶべき。
- エージェントがオブザーバビリティの MCP で問い合わせできたフレーキーなテストを、ユーザーが説明する。ルーティング: デバッグのスキルが、オブザーバビリティの MCP に触れるべき。
- エージェントがチャットの MCP で取得できたチャットスレッドを、ユーザーがリンクする。ルーティング: 該当するスキルが、チャットの MCP に触れるべき。

次の点を探してください:
- エージェントが自分で見つけなければならなかったツールの呼び出し方とコマンドフラグ

## 対象を、セッションが実際に使ったスキルとツールに絞る

所見は、このトランスクリプトが使ったスキル、ツール、MCP にだけ回してください。スキルが使われたとみなすのは、トランスクリプトがその `SKILL.md`（`.cursor/skills/`、`~/.cursor/skills/`、`~/.cursor/plugins/` の下）の `Read` を示す場合、そのパスを名指しした `Task` プロンプトがある場合、またはそのスキルに書かれたコマンドに一致するツール呼び出し（Shell、Grep、MCP など）がある場合です。親エージェントが一度も開いていないスキルへの推測的なルーティングは数えません。

所見の形は 2 つだけ有効です:
- 親エージェントがスキルを使い、あなたがその本文に本当の欠けを見つけた。スキルの該当する節に回します。
- スキルはカタログに見えていたが、役に立ったはずの場面で発火しなかった。将来のエージェントが拾えるように description を調整します。`tune description: <skill path>` として回します。

使われもせず、発火しそこねの候補でもないスキルは落としてください。

耐久性のある学びをそれぞれ挙げてください。各項目について:
- 原則: 慣習や技術的事実を 1 文で。将来のエージェントが、いつ当てはまるか分かる程度に具体的に。
- 証拠: トランスクリプトの正確な箇所（ターン番号か短い引用。コマンドやフラグも含める）。
- ルーティング: 最も関係する既存スキル（トランスクリプトに示されているとおりの `SKILL.md` のパス）、またはそのスキルが発火すべきだったのにしなかった場合は `tune description: <skill path>`、そうでなければ "new skill: <kebab-name>"。

些細なこと（誤字、再試行）と、親エージェントが従ったスキルからすでに明らかなことは飛ばしてください。ずれていく実装の詳細（特定の SHA、現在のファイルパス、バージョン番号、正確なバイト数）も飛ばしてください。慣習は一般化します。固定された詳細はしません。
