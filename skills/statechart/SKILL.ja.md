# ステートチャート（Statechart）

チャートは、システムが状態の間をどう動くかを、それを読む人の言葉で示します。その人、つまり読み手が、振る舞いが正しいかを決めます。

## 実行

リポジトリの外のスクラッチフォルダで作業します。TLA+ の仕様とその設定を書きます。それから次を実行します。

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` は TypeScript なので、TypeScript を実行できるランタイムで走らせます。

初回の実行では、mise で TLC と Java をインストールするため、ネットワークが必要です。

## 仕様を書く

- 読み手が同意する各ルールを INVARIANT として書きます。ルールは画面、結果、保存された値、メッセージのどれについてでも構いません。モデルにそのルール用の変数がなければ、変数を足します。ルールが成り立つように弱めてはいけません。
- `Next` は、`YouPressPlay \/ YouPressStop` のように、アクションの選言として書きます。そうしないと、TLC はすべてのステップを `Next` と名付けます。
- 出ていくステップのない状態は `NoDeadlock` を破ります。それが正しい終了状態であってもです。INVARIANT か PROPERTY がすでにその名前を使っているときは、ルールは `CHECK_DEADLOCK` です。`Next` に、終了状態でだけ真になり、何も変えないアクションを足します。たとえば `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars` で、`step()` でそれにラベルを付けます。

## チャートを選ぶ

判断が要る作業はあなたがやります。各状態と矢印に載せる言葉、フェーズとその色、タイトル、読み手へのレポートです。自分の仕事はビューモジュールに置き、`--view` で渡します。

読み手の言葉を示すため、ビューは `state(vars)` をエクスポートします。`state()` が返す値が形を決めます。

- 文字列ならフラットなチャートになります: `export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 配列なら親状態になります: `export const state = (v) => v.main.split(".");`
- オブジェクトならキーごとに 1 つの並列リージョンになります: `export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

各状態には、読み手が見られる、または気にするものをラベルにします。たとえば "Paying" や "Lease held, write pending" です。変数名はラベルに入れません。`vars` では、TLA+ のシーケンスは 1 から始まるキーを持つオブジェクトなので、`v.pc[1]` は `pc[1]` です。集合は配列です。

ビューは `step(action, from, to)` もエクスポートできます。TLC のアクション名と、ステップの前後の値を受け取り、矢印のラベルを返します。各ステップのラベルは、ユーザーが見る通りに書きます。たとえば "you press play" や "the connect fails" です。コードや TLA+ のアクションを名指ししてはいけません。チャートで同じ結末になる 2 つのアクションには同じラベルを付け、1 本の矢印を共有させます。

ステップが一部の条件でしか起きないときは、ラベルの末尾に、読み手の言葉で条件を角括弧に入れます。たとえば `you press play [while the file loads]` です。リージョンのチャートでは、コマンドが他のリージョンの条件を、そのラベルの言葉で矢印に書きます。たとえば `[when Offline]` です。あなたの角括弧はそれを置き換えるので、1 つの状態からの 2 本の矢印が同じに見えることがあります。ですからリージョンのチャートでは、他のリージョンの条件に角括弧を書かないでください。どのラベルにも示されない値がステップの行き先を決めるときは、結果をラベルに書きます。たとえば "the roster read fails" です。

ビューは次のものもエクスポートできます。

- `group(vars)` はフェーズの名前を返します。各チャート状態は、そのグループの色になります。1 つのチャート状態の背後のモデル状態が異なるグループにまたがるとき、その状態は色を持ちません。
- `colors` は各グループ名に色クラスを与えます。
- `title` はチャートが上部に表示する文字列です。

コマンドは `state()` と `group()` を各モデル状態につき最大 1 回、`step()` を各ステップにつき最大 1 回呼びます。チャートとレポートの両方がその答えを使います。ですから各関数は引数だけに依存させてください。

チャートは、1 つのラベルの中に留まるステップは描きません。読み手がそのステップを見る必要があるなら、ラベルを分けます。

矢印は 20 本程度以下を目指します。混みすぎたチャートは読みにくいからです。まず `state()` からより粗いラベルを返します。同じように振る舞う値には 1 つのラベルを与え、読み手に不要な細部は省きます。たとえば、呼び出し中で戻り値が何も変えないものなどです。バグ経路の各状態は保ち、各マークも保ちます。マージが `breaks` の状態を `mayBreak` に変えると、ルールがどこで破れるかが隠れます。別々のルールを破る 2 つの状態をマージしてはいけません。読み手が、どのルールがどこで破れるかを見られなくなるからです。それでもチャートが混みすぎるなら、読み手に不要なステップについて `step()` から `null` を返します。すべての状態にあるリセットや、他の矢印が示すことを繰り返すだけのステップです。ステップを隠すときは、次のルールに従います。

- 各チャート状態は、開始状態から矢印で到達できるように保ちます。
- モデルで出ていくステップがある各チャート状態から、少なくとも 1 本の矢印を保ちます。
- 1 本の矢印のステップは全部隠すか、まったく隠さないかです。一部だけ隠すと、その条件が狭くなります。
- 引き継ぎで、チャートが隠したステップを伝えます。

## レポートを読む

- チャートで、ルールを破る状態は `breaks` クラスを持ちます。背後のモデル状態の一部だけがルールを破るときは、`mayBreak` クラスを持ちます。凡例が各マークのルールを名指しします。2 つのルールが破れるときは、1 つのマークに両方を示すので、引き継ぎでどの状態がどのルールを破るかを伝えます。リージョンのチャートでは、ある状態を含むリージョン状態の組み合わせすべてがルールを破りうるときに、その状態にマークが付きます。ある組み合わせがルールを破りうるのに、そのどの状態にもマークがないときは、その組み合わせの各状態にマークが付きます。
- TLC はルールを破る状態を通り過ぎるので、チャートはバグの後の状態も示します。
- TLC はバグを通り過ぎるので、状態数に制限のないモデルは終わりなく走りえます。定数を小さく保つか、CONSTRAINT を足します。
- VIEW か SYMMETRY があると、TLC は同じものとして扱う状態を 1 つと数え、チャートはその 1 つの状態を描きます。矢印が、ステップが到達する状態ではなく、そちらへ向かうことがあり、レポートはそう述べます。
- TLC は CONSTRAINT や ACTION_CONSTRAINT の先の各状態でもルールをチェックしますが、その状態を探索せず、デッドロックもチェックしません。ルールの TLC の最短経路がそういう状態で終わるとき、チャートはその状態を描き、レポートはその経路を示します。チャートは境界の先の他の状態を描きません。そういう状態のデッドロックは表れません。TLC はまた、ACTION_CONSTRAINT が除外する各ステップの後でもルールをチェックします。別の経路で次の状態に到達するときも同じです。ルールの TLC の最短経路がそういうステップで終わるとき、チャートはそのステップを描きます。
- コマンドは、書かれたままの設定で、1 ワーカーで TLC によりルールをチェックします。ルールが破れると、そのルールを外して TLC を再実行し、破れるルールがなくなるまで続けます。最初の破れのあと、各実行は 10 万の異なる状態で止まるので、大きなモデルが終わりなく走ることはありません。実行がその上限に達するか、エラーで止まると、レポートは "Rules not checked" の下に、チェックしなかったルールを並べ、チャートはそれらにマークを付けません。チェックされていないルールは、成り立つことも破れることもあります。チェックするには、破れるルールを設定から外すか、モデルを小さくします。上限は、TLC の変数の順序を変えるモジュールを足すので、性質によっては、上限のない実行とは違う反例を TLC が見つけることがあります。
- `tlc.out` は、書かれたままの設定で TLC が出力したものです。チャートが、破れるルールのバグ経路を示さないときは、`tlc-RULE.out` が、それを見つけた実行で TLC が出力したものです。TLC が最初の警告を繰り返すとき、素の TLC はそれを 2 回出力しますが、`tlc.out` には 1 回だけ出ます。TLC が 2 つ目のコピーを、このコマンドが読む出力から外すからです。それが起きるのは、Java が `-XX:+UseParallelGC` で走るときだけです。そうでなければ TLC の最初の警告は、そのフラグを渡せという助言で、それは 1 回だけ出力されます。

## チャートを見せる

`chart.mmd` を `mermaid` のコードブロックとしてユーザーに見せます。チャートには 500 状態の予算があり、書かれたままの設定で TLC が数えます。それを超えると、チャートは破れるルールへの経路だけを描き、破れるルールがないときは、コマンドは `chart.mmd` を書き出しません。それでも各ルールをチェックし、レポートは状態数と各バグ経路を示します。グラフ全体を見るには、モデルを小さくします。

チャートは Pele でレンダリングします。ユーザーが画像を求めたとき、またはチャートがテキストとして読むには大きすぎるときは、`references/render.md` に従います。ユーザーが求めない限り、別のレンダラを使ってはいけません。

## 引き継ぐ

各チャートとその Mermaid のテキストを、判断しなければならない人に渡します。バグごとに 1 行を足します。ルール、そのルールについての読み手の文、レポートが番号を振る経路です。モデルが何を省いたかを伝えます。ファイルを作り直すコマンドを、新しい `--out` フォルダ付きで渡します。

モデルがコードを記述しているときは、各バグ経路を実際のコードに対して、テストかライブの再現として、アクションごとに 1 ステップで再生します。バグが起きないなら、起きないと示すまでは、モデルが間違っていると考えます。
