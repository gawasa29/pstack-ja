# TDD によるバグ修正（TDD Bug Fix）

明確で安いテスト経路があるバグを直すときは、プロダクションコードを変える前に、壊れた振る舞いを実行可能にします。目標は、修正の前に失敗し、修正のあとに通る、焦点の絞られたリグレッションテストです。

非現実的なときはテストを無理に作りません。使えるテストが、大掛かりなハーネスの準備、脆いモック、遅いエンドツーエンドの基盤、本番でしかない状態、曖昧な再現手順、無関係な大量のフィクスチャの変更を必要とするなら、新しいテストを足さず、最も近い有用な検証を使います。

## 手順

1. **バグを理解する。** 意図した振る舞い、現在の振る舞い、影響を受ける経路、最も小さく観察可能な再現を特定します。
2. **最も狭い実行可能なチェックを選ぶ。** そのコード経路で既に使われている、最も近いユニット、コンポーネント、統合、リグレッションテストを優先します。実用的なテスト経路がすぐに見えないなら、手順を満たすためだけに一から作ってはいけません。
3. **まず落ちるテストを書く。** そのバグを捕まえられたはずの、最も小さく焦点の絞られたテストを足します。テストは意図した振る舞いを符号化するもので、現在の実装を写し取るものではありません。
4. **直す前に新しいテストを実行する。** 意図した理由で失敗することを確認します。通ってしまうか、無関係な理由で失敗するなら、実装を編集する前にテストか再現を直します。
5. **バグを直す。** 近くの契約を保ちながら、意図した振る舞いを満たす最小のプロダクションコードの変更を行います。
6. **リグレッションテストを再実行する。** テストが今は通ることを確認します。

## 落ちるテストが非現実的なとき

代わりに、最も近い実行可能なリグレッションのチェックを使います。狙いを絞ったスクリプト、手動の再現コマンド、ブラウザ自動化、スナップショット比較、ログの assert、焦点を絞った統合チェックです。

新しいテストを足さない方が、悪いテストよりましです。悪いテストとは、ほとんどモックをテストするもの、現在の実装の詳細を符号化するもの、タイミングや無関係なグローバル状態に依存するもの、小さな修正のために高価な基盤を必要とするもの、修正を証明した直後に削除されるもののことです。

## 守るべき線

- 間違った実装に合わせるためだけにテストを変えてはいけません。
- 期待する振る舞いが本当に変わり、その理由が明確な場合を除いて、既存の assert を弱めてはいけません。
- リグレッションテストはそのバグに集中させます。広範なフィクスチャの変更や、無関係なカバレッジの拡大は避けます。
- バグがフレーキーなら、可能な範囲でテストを決定的にし、何のシグナルを固定しているかを記録します。
- バグがより広い種類の失敗を明らかにするなら、まず焦点を絞ったリグレッションの経路を取り込み（land）、そのあとで同種の追加カバレッジを検討します。

## 最終的な返答

結果だけでなく、証拠を報告します。

- 修正前に落ちたテストか実行可能なチェックと、それが生んだ失敗を名指しします。
- 修正後に通ったテスト実行と、その周辺で行った検証があれば名指しします。
- 修正前に落ちたという証拠を示せなかったなら、その理由を述べ、代わりに使った最も近いリグレッションのチェックを説明します。
