# TypeScript のベストプラクティス

まず **type-system-discipline** 原則スキルを適用します。

| ルール | 概要 |
|------|---------|
| 判別可能ユニオン | バリアントを `kind` のリテラルな判別子で表し、不可能な状態を表現できないようにします。省略可能フィールドの寄せ集めは使いません。 |
| ブランド型 | プリミティブに `& { readonly __brand: "X" }` を付けてブランド化し、取り違えられないようにします。検証は境界で 1 回だけ行います。ブランドは検証する型ガード（`input is AgentId`）から得るもので、`as` からは決して得ません。 |
| 構成的なモデリング | 不正な値を作れない形に組みます。非空なら `[T, ...T[]]`、偶数長なら `[T, T][]`、範囲なら `start` と `duration` です。実行時のガードでも、refinement types への願望でもありません。 |
| 最も単純な全域型 | その型に対するすべての操作が全域（total）のままである限り `T[]` を保ちます。緩い型が `!`、キャスト、「起こらないはず」の throw を強いる箇所だけ `NonEmpty<T>` に強めます。 |
| `any` より `unknown` | 外部データは `unknown` です。 |
| ガードよりスキーマ | プロパティごとの型ガードを手書きする前に、リポジトリの実行時スキーマライブラリを使い、`z.infer` のようにスキーマから型を推論します。 |
| `as` キャスト禁止 | `as` はどれも、待機中の実行時クラッシュです。キャストは検証の後だけにします。 |
| 絞り込みの階層 | 判別子の switch > `in` 演算子 > `typeof`/`instanceof` > ユーザー定義の型ガード > `as`。 |
| 型ガード | 主張を検証しなければなりません。嘘をつくガードは `as` より悪いです。バグが「安全だ」と主張する名前の陰に隠れるからです。名前は `isX` か `hasX` にします。 |
| 網羅性 | default 節に `const _exhaustive: never = x;` をインラインで置き、新しいバリアントが増えたらコンパイラがエラーを出すようにします。 |
| `as` より `satisfies` | リテラル型を広げずに値を検証します。 |
| 境界での検証 | データが入ってくる境界でパースし、名前付きのドメイン型にします。`Record<string, unknown>`（綴りがどうであれ）はそのパースで止まります。内側では型を信頼します。**boundary-discipline** 原則スキルを参照してください。 |
| スキーマ由来の型 | 新しい interface を宣言する前に、`Pick`/`Omit`/`Parameters`/`ReturnType`/`Awaited`/`typeof` に手を伸ばします。 |
| オブジェクト引数 | 位置引数ではなくオブジェクトを渡し、引数の順序が自己文書化されるようにします。ホットパス（フレームごとの描画、トークナイザ、パーサ）では省きます。 |
| 本物のテスト | 実行できるものをモックしません。リーク・破棄のチェックを備えたフレームワーク本来のテストプリミティブを優先し、UI は動いているビルドで検証します。ローカルで実行できないものだけをモックします。 |
| 構造化テレメトリ | 構造化ロガーの診断を優先し、id からデバッグできるだけの文脈を持たせます。出荷するコードに `console.log` は入れません。 |
