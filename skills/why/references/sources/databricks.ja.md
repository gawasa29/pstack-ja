# Databricks の分析とシステムテーブル

## このソースに含まれるもの

Databricks は、プロダクト分析、データパイプライン、ウェアハウスのテレメトリの層です。Datadog を補完します。Datadog が*インフラ / 実行時*の視点なら、Databricks は*プロダクト / データ*の視点です（ユーザーが何をしたか、どの実験が走ったか、機能の利用がどう推移したか、しきい値の定数がどこから来たか）。

- **プロダクト分析のイベント。** `your_warehouse.events.analytics_track_event`（生データ）と、`<your_analytics_db>.<schema>.<table>` にある、型付きで重複排除されたイベントごとの dbt モデル。ユーザーの行動: 機能の呼び出し、クリック、承認 / 拒否、送信、クライアントが報告したエラー。
- **利用と課金のイベント。** `your_warehouse.events.usage_event` / `<your_analytics_db>.<schema>.stg_usage_events`、`your_warehouse.events.raw_model_event` / `<your_analytics_db>.<schema>.stg_raw_model_events`。コストや量に駆動された判断のため。
- **実験 / フィーチャーフラグのデータ。** 曝露（exposure）と結果のテーブル。**スキーマは企業ごとに異なります。** 名前を決めつける前に `SHOW TABLES` で確かめてください。
- **システムテーブル。** `system.query.history`、`system.compute.warehouses`、`system.billing.*`、`system.access.audit`。「このクエリは高くついたか」「誰かがこれを実行した頻度は」「ウェアハウスの負荷が跳ねたのはいつか」に答えます。
- **dbt のリネージ。** `<your_analytics_db>.<schema>` のモデルは、どのパイプラインがテーブル / フィールドに依存しているかを明らかにします。上流の変更が、消費側のコードの変更の動機になることはよくあります。
- **Databricks のノートブック。** エンジニアがコード変更の前に書いた探索的な分析。**SQL の MCP からは問い合わせできません。** 根拠がノートブックにある疑いがあるなら、ギャップとして名指ししてください。

## 検索の仕方

Databricks SQL の MCP を使ってください。主なツールは `execute_sql_read_only` です。`statement_id` が返ったら、再実行せずに `poll_sql_result` でポーリングしてください。

**問い合わせる前に位置を把握します。** スキーマは企業ごとに異なります。テーブル名を信じる前に確かめてください:

```sql
SHOW TABLES IN <your_analytics_db>.<schema> LIKE '*<keyword>*';
DESCRIBE TABLE <your_analytics_db>.<schema>.stg_<event>;
```

**すべてのクエリに期間を付けます。** これらのテーブルは巨大で、制約のないスキャンはタイムアウトします。`_timestamp`（イベント）または `start_time`（`system.query.history`）で、出荷日をはさむ期間に絞ります。ふつうは前後 30 日程度、よほどの理由があるときだけ広げてください。

**生のテーブルより、型付きの dbt モデルを優先します。** `<your_analytics_db>.<schema>.<table>` は重複排除され、型が付き、liquid clustering されています。`your_warehouse.events.analytics_track_event` には重複と、型のない `properties_json` があります。モデル名のパターンは `stg_<source>_<event_name_with_underscores>` で、`<source>` は `app`、`backend`、`website`、`cli` のいずれかです。パターンだけでは特定できないときは、`SHOW TABLES` で正確なモデル名を確認してください。生のテーブルに降りるのは、まだ dbt モデルがない場合か、dbt のリフレッシュ遅延の中にあるイベントが必要な場合だけです。

**型付き dbt モデルのカラムの慣習**（知っておくと `DESCRIBE` の往復を省けます）:

- `_timestamp`、`_id`、`_auth_id`、`_request_id`、`event_name`。すべてのモデルで標準
- `properties_<name>`。型付きで、アンダースコア区切りのイベントプロパティ（`properties_entrypoint`、`properties_size_bytes`、…）
- `context_team_id`、`context_client_version`、`context_country`、`context_client_os`。事前に抽出されたクライアントの文脈

### 報われやすい調査のパターン

対象に合うテーブルとカラムの組み合わせを選んでください:

1. **イベント利用の推移。** PR のマージをはさむ ±30 日の期間で、該当する `stg_*` モデルの日次件数。マージから 1、2 日以内にゼロから安定した量へ段状に変わるのは、その PR が機能を立ち上げた強い状況証拠です。ゼロへ減衰するのは、非推奨化や削除を示唆します。
2. **ガードレール / 防御チェックの由来。** PR の*前* 14 日間における、該当する `properties_<name>` カラムの分布（中央値 / p99 / 最大）。p99 が対象のしきい値の定数と一致するなら、その数値はデータから選ばれたことを示唆します。
3. **実験 / フィーチャーフラグの照会。** `SHOW TABLES ... LIKE '*experiment*'` で曝露テーブルを見つけ、PR の日付の近くで、該当するフラグキーのバリアント別の曝露数を取得します。
4. **マイグレーション、バックフィル、性能の書き換えに対するクエリ履歴の証拠。** `system.query.history` を `statement_text ILIKE '%<table_or_symbol>%'` で絞り、`start_time` の狭い範囲で見ると、変更の動機になった可能性が高い高コストなクエリが見つかります（`total_duration_ms` で並べ替えるか、`SUM(read_bytes)`、`COUNT(*)` で集計します）。
5. **dbt のリネージ。** 対象が `<your_analytics_db>.<schema>` のモデルを読み書きしているなら、そのモデル自身の git 履歴（このリポジトリ内）に根拠があることがよくあります。その手がかりは自分で追わず、git の調査担当に渡してください。

## ここでの良い証拠とは

上のパターンの形に加えて:

- 防御的なコードの PR のあと数日で、エラーを分類するイベントの件数がほぼゼロまで下がる。その PR がそのエラークラスを解消したことを示唆します
- 曝露テーブルの行が、PR の出荷日の前後に「shipped」/「concluded」の決定とともに、対象のフィーチャーフラグのキーを名指ししている

## よくある落とし穴

- **計測されている ≠ 原因。** イベントが存在するのは、誰かが記録する価値があると思ったからであり、そのイベント*ゆえに*対象のコードが存在するわけではありません。因果を主張する前に、git の調査担当からの PR / コミットの引用と組み合わせてください。
- **静かな計測の変更。** イベント量の段状の変化は、ユーザーの行動が変わったのではなく、新しいイベントの記録が始まっただけかもしれません。その立ち上がりを機能リリースのシグナルとして読む前に、同じ期間の計測用の PR を確認してください。
- **スキーマの変化。** イベントのプロパティは進化します。今の型付き dbt モデルのカラムが、対象が書かれた当時には存在しなかったかもしれません。古いデータでは、プロパティが生の `properties_json` の中にしかないことがあります。
- **dbt のリフレッシュ遅延。** `<your_analytics_db>.<schema>.*` はスケジュール（多くは毎時 / 毎日）で再構築されます。直近数時間のイベントは `your_warehouse.events.*` に切り替え、`_id` で重複を排除してください。
- **企業ごとに異なるテーブル。** 実験、フィーチャーフラグ、課金、利用のテーブルはさまざまです。存在を確認していないテーブルの結果を報告するのは、典型的な失敗パターンです。まず `SHOW TABLES` / `DESCRIBE TABLE` で確かめてください。
- **保持期間の崖。** 該当する期間が、テーブルの保持期間や dbt モデルの作成日より前なら、それは*ギャップ*であり、該当なしの結果ではありません。統合担当が「結果なし」を「活動なし」と読まないよう、明示的に名指ししてください。
- **ノートブックは問い合わせできません。** SQL の MCP からは Databricks のノートブックが見えません。根拠がそこにある疑いがあるなら、ギャップとして返してください。

## 返すもの

関連する発見ごとに:
- 種類（プロダクトイベント / 実験の曝露 / 利用または課金のイベント / システムテーブルの行 / dbt モデル）
- 完全修飾のテーブル名と、実行したクエリそのもの
- 問い合わせた期間
- 簡潔な数値の要約（件数、パーセンタイル、初回 / 最終観測のタイムスタンプ）。**生の行を吐き出さないこと。**
- 対象の出荷日との時間的な相関（例:「最初の行 2024-08-15、PR #49074 は 2024-08-14 にマージ」）
- 関連性と強さ: direct / circumstantial / weak
