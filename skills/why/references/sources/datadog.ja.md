# Datadog のテレメトリ

## このソースに含まれるもの

Datadog は、計画や議論ではなく、本番で実際に起きたこと、つまり実行時の記録を持っています。

- **メトリクス。** チームが仕込んだカウンタ、ゲージ、ヒストグラム。メトリクスが*存在する*こと自体が、誰かがその数値を監視する価値があると考えた証拠です。
- **モニターとアラート。** 誰かを起こす価値があるとチームが判断した条件。`rate_limit_hit > 10/min` で発火するモニターは、チームがそのしきい値を気にしていた直接の証拠です。
- **ダッシュボード。** チームがサブシステムにとって重要だと考えているものを厳選したビュー。
- **APM のトレースとスパン。** リクエスト単位の実行時データ。「なぜ遅いのか」「なぜここでタイムアウトするのか」という問いに使います。
- **ログ。** 大量のイベント記録。防御的なコードの動機になったエラー条件が入っていることがよくあります。
- **インシデント。** タイムラインとポストモーテムのリンクを伴う正式なインシデント記録。
- **ノートブック。** チームの探索的な調査。仮説と分析が含まれることがよくあります。

## 検索の仕方

Datadog の MCP を使ってください。まず広く、そのあと絞ります。

1. **所有しているサービスを特定します。**

   ```
   search_datadog_services (filter by name or team)
   search_datadog_service_dependencies (see upstream/downstream)
   ```

2. **まずダッシュボードとモニター。**

   ```
   search_datadog_dashboards (query: feature name, service name, symbol)
   search_datadog_monitors   (same queries)
   ```

   ダッシュボードやモニターが対象をカバーしているなら、そのクエリと監視しているしきい値を記録します。しきい値が「なぜ N で clamp しているのか」の答えであることはよくあります。

3. **対象の周辺のメトリクス。**

   ```
   search_datadog_metrics (by name pattern, e.g., the feature or symbol)
   get_datadog_metric_context (metadata: description, units, tags)
   get_datadog_metric (timeseries; "was there a spike around the PR date?")
   ```

   メトリクスの推移を対象の追加 / 変更日と相関させることは、強い裏付けになります:「`payment_timeout` メトリクスが 2023-11-03 に急増し、リトライのロジックが 2023-11-06 にマージされた」。

4. **ログ。絞り込むのであって、吐き出させないこと。**

   ```
   search_datadog_logs (raw log patterns near the target, set use_log_patterns=true)
   analyze_datadog_logs (SQL-style aggregations, only when you need counts)
   ```

   シンボル、エラー文字列、機能名で検索してください。**期間を絞ったクエリを強く優先します**（例: 変更の前後 30 日）。

5. **APM のスパンとトレース。**

   ```
   aggregate_spans    (stats: "how often does this endpoint fail?")
   search_datadog_spans (inspect individual spans)
   get_datadog_trace  (a specific trace ID)
   ```

   タイムアウト、リトライ、遅い経路、サービスをまたぐ振る舞いに役立ちます。

6. **インシデント。**

   ```
   search_datadog_incidents (by title, team, date range)
   get_datadog_incident     (full detail for a specific incident)
   ```

   対象が防御的に見えるなら、それが追加された時期の前後のインシデントを検索してください。タイムラインに「X の防御チェックを追加」とあるインシデントは、ほぼ直接の証拠です。

## ここでの良い証拠とは

- クエリとしきい値が、コードが強制している制約と一致するモニター（コードは 100 に clamp し、モニターはリクエストが 100/min を超えるとアラートする）
- 対象の作成者が作ったダッシュボードで、ウィジェットがコードの計測対象や防御対象に対応しているもの
- コードがマージされる直前に本番の急増を示し、そのあと安定した値になるメトリクス
- 対象のコード、同じシンボル、または同じエラー文字列に言及したインシデント記録
- 防御的なコードが防ぐはずの特定のエラーパターンを示すログで、変更前の期間にタイムスタンプがあるもの

## よくある落とし穴

- **相関は因果ではありません。** PR の前の急増とその後の安定は示唆的ですが、決定的ではありません。同じ期間に他の変更が入っているかもしれません。近くの PR を確認してください。
- **見つけたグラフへの過剰適合。** グラフは作った人の枠づけを反映します。「retry success rate」という名前のグラフは、チームがリトライの成功率を気にしていた証拠であって、特定のコード行が存在する理由の証拠ではありません。
- **消えたテレメトリ。** メトリクスは名前が変わったり、削除されたり、保持期間が短かったりします。該当する期間のデータが見つからないなら、それはギャップであり、該当なしの結果ではありません。
- **規模に伴うノイズ。** ログ検索はサービス、タグ、期間で積極的に絞ってください。生のログを吐き出すのではなく、`analyze_datadog_logs` で集計します。
- **計測されている ≠ 原因。** メトリクスは、誰かが測る価値があると思ったことを示すのであって、そのコードが*それゆえに*追加されたことを示すのではありません。コミット / PR の日付と突き合わせてください。

## 返すもの

関連する項目ごとに:
- 種類（ダッシュボード / モニター / メトリクス / ログパターン / トレース / インシデント / ノートブック）
- タイトルまたは名前
- リンクまたは識別子（ダッシュボード ID、モニター ID、メトリクス名、インシデント ID）
- 所有者 / 作成者と作成 / 変更日
- 問いに関わる具体的な条件、クエリ、引用（可能ならそのまま）
- 関連性: 対象のコードについて何を示唆するか、つながりがどれだけ強いか
