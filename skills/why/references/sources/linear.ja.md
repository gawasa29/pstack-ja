# Linear のチケット

## このソースに含まれるもの

- 機能やバグ、その動機を述べたイシュー
- イシューに添付されたプロジェクトのドキュメント（多くの場合 PRD や仕様）
- 親 / サブイシューの関係（より広い取り組み → 個別のチケット）
- イシューへのコメント（明確化、範囲の変更、「なぜやるか」の根拠）
- 動機の種類を示すラベル（例: `compliance`、`customer-request`、`perf`）
- 範囲の変更を説明するステータスの更新
- 添付ファイルと、リンクされた GitHub の PR

プロダクトやビジネスの文脈は、しばしば Linear にあります。「顧客 X の要望でやっている」「これは Q3 のコンプライアンス施策のため」という層です。

## 検索の仕方

Linear の MCP を使ってください。

1. **リンクされたチケットから始めてください。** シードのコミットや PR がチケット ID（例: `ENG-1234`、`[BUG-567]`）を参照しているなら、まずそれらを `get_issue` で取得します。コメントも含めてイシュー全体を読みます。
2. **キーワードで関連するイシューを一覧します。** `list_issues` をテキスト検索付きで使い、機能名、主要なシンボル、ビジネスの用語で探します。複数の言い回しを試してください。
3. **イシューの木をたどってください。** サブイシューに着地したら、その親を取得します。サブイシューは戦術的です。親が「why」を持っていることがよくあります。
4. **プロジェクトのドキュメントを読んでください。** イシューがプロジェクトに属しているなら、`get_project` を使って添付ドキュメントを確認します。仕様と根拠がもっともよく記録されるのは、プロジェクトレベルのドキュメントです。
5. **ラベルとマイルストーンを確認してください。** ラベルは動機のカテゴリ（customer-request、incident-followup、compliance）をほのめかします。マイルストーンは作業を締め切りに結びつけ、動機が明らかになることがよくあります。

## ここでの良い証拠とは

- ビジネス上の問題を述べたイシューの説明:「顧客 Acme は SOC2 監査のため X を必要としている」
- 決定を記録したコメント:「アプローチ A は課金サービスに手を入れる必要があるので、B で進めることにした」
- 取り組み名のようなタイトルの親イシュー:「Q3 Enterprise Readiness」「Reduce Payment Failures」
- 添付された PRD や仕様
- `customer:acme`、`incident-followup`、`compliance`、`perf-regression` のようなラベル

## よくある落とし穴

- **範囲のずれ。** PR が参照するチケットが、いったん閉じられて別の範囲で開き直されているかもしれません。履歴全体を読んでください。
- **機械的なテンプレート。** 「Why」セクションを必須にしているのに、定型文で埋めているチームもあります。一般的な文言（「ユーザー体験の向上」）は、おそらく本当の答えではありません。
- **古いチケット。** 古いチケットは、変わったあとの計画の版を反映していることがよくあります。日付を確認し、コードの出荷日と突き合わせてください。
- **重複として閉じられた連鎖。** 重複元の関係をたどって、正規のチケットまで戻ってください。
- **プライベートなワークスペースの内容。** イシューにアクセスできないなら、推測せずギャップとして記録してください。

## 返すもの

関連するチケットごとに:
- チケット ID とタイトル
- 問題 / 動機を説明やコメントから引用したもの（言い換えないこと。統合担当は引用するために正確なテキストを必要とします）
- ラベル、親イシュー、プロジェクト
- 作成者、作成日、クローズ日
- 可能ならチケットへのリンク
