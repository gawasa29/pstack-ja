# Notion のドキュメント

## このソースに含まれるもの

- PRD（プロダクト要求仕様書）
- 技術仕様と RFC
- アーキテクチャ決定記録（ADR）
- 設計レビューの議事録
- ドメインの文脈をまとめたチームページ
- インシデントのポストモーテム
- 防御的なコードを説明しているかもしれないランブック
- 優先順位を定める戦略ドキュメント

why は、コードになる前の長文として、しばしば Notion にあります。重要な機能にはたいていドキュメントがあります。

## 検索の仕方

Notion の MCP を使ってください。

1. **`notion-search` でキーワード検索します。** 次を試してください:
   - 機能名
   - 対象のコードにある主要なシンボル / クラス名
   - 作成者のハンドル（設計ドキュメントはコードが入る前に書かれることがよくあります）
   - エラー文字列やユーザーに見える用語
   - コードの出荷時期がわかっているなら、期間を絞ったクエリ
2. **候補のページを `notion-fetch` で取得します。** プレビューではなく全文を読みます。根拠はドキュメントの中ほどに埋もれていることがよくあります。
3. **バックリンクと子ページをたどります。** 設計ドキュメントには、検討した代替案、付録、実装メモのサブページがあることがよくあります。
4. **関連するデータベースを確認します。** `notion-query-data-sources` と `notion-query-meeting-notes` で、その決定を議論した議事録が見つかることがあります。
5. **作成者固有のスペースを検索します。** PR の作成者が個人のノートブックを持っているなら（一部の企業ではよくあります）、コードに先立つ探索的な思考がそこにあるかもしれません。

## ここでの良い証拠とは

- 「Problem statement」や「Motivation」のセクションがあり、対象のコードの目的と一致する PRD
- 「Alternatives considered」や「Rejected approaches」のセクション
- 対象のコードを、特定のインシデントの修正として名指ししたポストモーテム
- 「Y という理由で X に決めた」と記録され、PR と同じ作成者 / 期間に結びつく議事録
- ADR のテンプレートが中身のある形で埋まっているもの（status、context、decision、consequences）

## よくある落とし穴

- **古くなったドキュメント。** 仕様は実装前に書かれ、更新されないことがよくあります。ドキュメントは、変わった計画を説明しているかもしれません。実際の PR と突き合わせてください。
- **ドキュメントと現実のずれ。** 仕様が「X をする」と言っていても、コードは実際には Y をしているかもしれません。ずれを明示してください。統合担当が矛盾として表に出します。
- **定型のテンプレート。** 「Why」セクションを必須にしている組織では、中身の薄い文章で埋められていることがあります。具体性を探してください。
- **リンクされていないドキュメント。** もっとも関連するドキュメントが、どこからもリンクされていないかもしれません。広いキーワード検索が助けになります。
- **複数の下書き。** ある話題に複数のドキュメントがあるなら、最終版になったもの、または最後に更新されたものを見つけます。日付を確認してください。
- **アクセス制限のかかったページ。** ページにアクセスできないなら、ギャップとして記録してください。

## 返すもの

関連するドキュメントごとに:
- タイトルと URL
- 作成者と最終更新日
- 動機のテキスト（逐語的な引用）。ページ / セクションの位置を添えます
- 関連するリンク先のページ（統合担当が引用できるように）
- ドキュメントが最終版か下書きか
